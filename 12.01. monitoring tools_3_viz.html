Slide 7

Events, suspicious behaviours and alerts

Every monitored system produces events. An event is one recorded occurrence: a logon, a failed logon, a file change, a firewall decision, a service that stops. The system stores each event as a log entry made of fields, such as the time, the host name, the account, the event number and the result. A small network records thousands of events every hour, and almost all of them describe normal work.

A suspicious behaviour is an activity, or a pattern of activities, that does not prove an attack but that appears often during attacks. Five failed logons in one minute, an administrator account created outside a planned change, a security log that is cleared: each one can have an innocent explanation, and each one deserves a look. Competency EZ01 (criterion 3.2) speaks of predefined suspicious behaviours, the behaviours that the monitoring team decides in advance to watch and writes down.

An alert is a notification produced by the monitoring tool when the collected data satisfy a written condition. That written condition is an alert rule, also called a detection rule. The tool evaluates its rules automatically on every incoming event. An alert is therefore a request for human attention, not a verdict: a person must examine the data and decide what happened.

Slides 8 and 9

The seven parts of an alert rule

A rule that can be configured, tested and reviewed answers seven questions. Write all seven for every rule, even when the tool does not need all of them.

  1. Data source: the log or the device that provides the evidence. For Val-des-Pins, the four sources of need N-01: FW-01, SRV-FILE-01, PC-ACCT-01 and SW-01.
  2. Match condition: the field values that an event must contain, for example Windows event 4625, "An account failed to log on".
  3. Count and time window: how many matching events are needed, within how much time, for example 5 within 120 seconds. Most tools use a sliding time window: at every new event the tool looks back over the last 120 seconds, so the window moves with time instead of starting at fixed clock times.
  4. Grouping key: the field that must have the same value in all the counted events, for example the account name. Without a grouping key, one failure from each of five different employees would be counted as one burst of five.
  5. Severity: how serious the possible consequence is (Lesson 3.5.3).
  6. Notification: who is told, through which channel and how fast (Lesson 3.5.3).
  7. Response note: the first checks that the person performs when the alert arrives, written in advance so that nobody has to improvise under pressure.

Slides 10 and 11

Five types of alert rules

Almost every alert rule belongs to one of five types. The type tells you what the tool must remember between two events.

  • A single-event rule fires on one event, because the event itself is rare and serious. Example: Windows event 1102, "The audit log was cleared". The tool remembers nothing.
  • A threshold rule, also called a frequency rule, fires when the number of matching events inside a time window reaches a value. Example: 5 failed logons for the same account within 120 seconds. The tool remembers the recent matching events.
  • A baseline-deviation rule, also called an anomaly rule, compares a measured value with the normal range learned from the baseline. Example: the hourly outbound traffic of PC-ACCT-01 above its normal maximum (Lesson 3.5.2). The tool remembers the statistics of the baseline.
  • A sequence rule, also called a correlation rule, fires when different events occur in a given order within a time window. Example: a successful logon less than 10 minutes after a burst of failures for the same account. Correlation means linking events, from one or several sources, that belong to the same activity. The tool remembers that the first event happened.
  • An absence rule, also called a heartbeat rule, fires when an expected event does not arrive. Example: FW-01 has sent no log line for 15 minutes. The tool remembers the time of the last event of each source. A missing log can come from a technical fault or from an attempt to hide activity; in both cases the monitoring team has lost visibility.

    Slide 19
    

    Why the number matters
    

    Threshold rules and baseline-deviation rules both need a number: the threshold, the value beyond which the tool raises an alert. The choice of this number carries two opposite risks. A threshold that is too low turns normal activity into false positives, alerts raised when nothing is wrong. A threshold that is too high lets real problems pass without an alert: these are false negatives. The baseline that you started in Lesson 3.4 is the evidence that lets you choose the number instead of guessing it.
    

    

    Static and baseline-derived thresholds
    

    A static threshold is a fixed number chosen from knowledge or from a policy, for example "5 failed logons in 120 seconds". It suits quantities whose normal value is close to zero, where any burst is unusual. A baseline-derived threshold, also called a dynamic threshold, is calculated from measurements of normal activity. It suits quantities that change with the hour and the day, such as traffic volume, the number of logons or the number of file changes.
    

    Slide 20
    

    Three statistics of a baseline
    

    For one metric, for example the megabytes sent per hour by PC-ACCT-01, three statistics describe the baseline.
    

      

    • The mean, or average, is the sum of the n measured values divided by n.
      • 

    • The standard deviation measures how far the values usually are from the mean. For a sample of n values, it is the square root of the sum of the squared differences from the mean, divided by n − 1. A small standard deviation describes stable activity; a large one describes activity that changes a lot.
      • 

    • A percentile is the value below which a given percentage of the measurements fall. The 99th percentile, written P99 (99th percentile), is the value that 99 % of the measurements do not exceed. With the nearest-rank method, you sort the n values and take the value at rank ⌈0.99 × n⌉, the smallest whole number greater than or equal to 0.99 × n.
      • 

    

    When the values follow a normal distribution (a symmetric, bell-shaped distribution), about 68 % of them lie within 1 standard deviation of the mean, 95 % within 2 and 99.7 % within 3. A threshold at mean + 3 × standard deviation would then be exceeded by about 0.13 % of normal hours. Monitoring data are often not bell-shaped, with many small values and a few large ones, so always compare the statistical threshold with the percentile and with the real counts of your baseline.
    

    Slide 21
    

    Profiles: one threshold per type of hour
    

    Normal activity at 10:00 on a Tuesday is not normal activity at 02:00 on a Sunday. Before calculating anything, split the baseline into profiles: groups of hours with similar activity. Val-des-Pins uses two profiles: office hours (Monday to Friday, 07:00 to 18:00) and off hours (all other hours). Each profile receives its own mean, its own standard deviation and its own threshold. A single threshold for all hours would be too high for the night and too low for the day.
    

    Slide 22
    

    The multiplier k, the floor and the expected false alarms
    

    Two decisions complete the threshold.
    

      

    • The multiplier k in "mean + k × standard deviation". A larger k gives fewer false positives but a higher risk of false negatives. Choose k by counting how many baseline hours exceed each candidate: those hours are the false alarms that you would have received during the baseline period, when no attack was known. Divided by the number of weeks of the baseline, the count gives the expected false alarms per week.
      • 

    • The minimum floor, an absolute value below which no alert is raised even when the value is statistically unusual. At night PC-ACCT-01 sends about 3.0 megabytes per hour; 14 megabytes is unusual for the statistics but too small to matter for the business. The floor, 25 megabytes per hour at Val-des-Pins, is a documented business decision, not a statistical result.
      • 

    

    threshold of a profile = the larger of (mean + k × standard deviation) and the floor
    

    Slide 23
    

    Keep the baseline clean and the thresholds current
    

    A threshold is only as reliable as the baseline behind it. Before you calculate, remove the periods with known incidents or planned exceptional work (a migration, a year-end closing), check that every day of the week is covered, and record the baseline period and the date of the calculation. Recalculate the thresholds when the baseline is updated (Topic 6.1) and review them at least once a month: the CIS (Center for Internet Security) Controlscheck safeguard 13.11 recommends tuning security event alerting thresholds monthly, or more frequently.
    

    Slide 24
    

    How Wazuh uses a calculated threshold
    

    For counts, the threshold is written directly in the rule: frequency="5" and timeframe="120" for AL-01. For a baseline deviation, remember that Wazuh rules compare fields but do not calculate means. A small script on MON-01 therefore calculates the hourly volume from the FW-01 records and writes one line per hour into a local log file, for example:
    

    VDP-VOLUME host=PC-ACCT-01 hour=02 mb=486.0 profile=off-hours threshold=25.0 status=ABOVE
    

    Wazuh reads that file like any other log (monitoring log filescheck), and a custom rule that matches status=ABOVE raises AL-07. The calculation stays in the script; the alert, its severity and its notification stay in Wazuh.

      Slide 29
      

      Severity and priority
      

      Severity measures how serious the possible consequence of the detected behaviour is. Priority is the order in which alerts are handled; it combines the severity with the importance of the asset (the priority tiers of Lesson 2.5) and with the time of day. A small organization needs one short scale, with a written definition for each level, so that two people give the same level to the same alert.
      

        

      • Critical evidence of an attack in progress, or of an attempt to hide activity, on a priority asset. Examples: AL-02, AL-05, AL-06.
        • 

      • High behaviour that often comes before an attack, or loss of visibility on a priority asset. Examples: AL-01, AL-04, AL-07, AL-08, AL-09.
        • 

      • Medium unusual behaviour with frequent legitimate causes. Example: AL-03.
        • 

      • Low information useful for context and trends, with no action required by itself. Example: an agent that reconnects after a restart.
        • 

      

      Slide 30
      

      Read the numbers in the right direction
      

      Tools number severities differently. Wazuh uses levels from 0 to 16, where a higher number is more serious; level 12 is described as a "high importance event" (rules classificationcheck), and by default the Wazuh manager stores alerts from level 3 upward. The syslog protocol, defined in RFC (Request for Comments) 5424 and published by the IETF (Internet Engineering Task Force) (text of the standardcheck), uses eight severities from 0, Emergency, to 7, Debug, where a lower number is more serious.       Notification channels and the Wazuh e-mail settings
      

      A notification channel is the way an alert reaches a person: the dashboard of the tool, a screen that someone must open; an e-mail; a text message sent by SMS (Short Message Service) or a phone call; or a ticket in a help-desk system. Faster channels interrupt people, so they are kept for the most serious levels.
      

      Need N-01 asks for an e-mail within 5 minutes for the four priority sources. In Wazuh, e-mail is enabled in the global section of ossec.conf (email_notification, smtp_server, email_from, email_to). Three default values matter (alert managementcheck, global optionscheck):
      

        

      • only alerts of level 12 or more are e-mailed (email_alert_level);
        • 

      • at most 12 e-mails are sent per hour, and the extra alerts are grouped into one e-mail at the end of the hour (email_maxperhour);
        • 

      • Wazuh cannot log in to a mail server that requires authentication, so it needs a local mail relay.
        • 

      

      Because High alerts are levels 10 to 12 in Table 3.5.C, AL-01 (level 10) would not be e-mailed with the default setting. In the isolated lab, e-mails go to a local mailbox on MON-01, never to a real external address (Legal Notice §6.4).
      

      Slide 32
      

      Recipients, acknowledgement and escalation
      

      Each level needs a recipient, named by role rather than by person so that the rule survives holidays and staff changes; an acknowledgement target, the maximum time before someone confirms "I am handling this alert"; and an escalation path, the next role to notify when nobody acknowledges in time. At Val-des-Pins the monitoring technician receives every alert, and the owner is called when a Critical alert is not acknowledged within 15 minutes.
      

      The company has no night staff. Critical alerts reach a person at any hour; High alerts that arrive at night are delivered at once but read at 07:00. That delay is an accepted risk: the owner decides it in writing, knowing that an event at 02:00 could be read five hours later. The written decision is what distinguishes an accepted risk from an oversight.
      

      Slide 33
      

      Alert fatigue and the four controls
      

      Alert fatigue is the decline in attention and in response quality that occurs when people receive more alerts than they can examine, especially when many of them are false. It can be measured: alerts left unread, acknowledgement times that grow, rules that everybody ignores. Four controls keep the volume within the capacity of the team.
      

        

      • Deduplication: one notification for repeated identical alerts (same rule, same host) within a time window, with a count of the repeats.
        • 

      • Grouping, also called aggregation: one message for several related alerts, for example the daily digest, one e-mail sent at 08:00 that lists all the Medium alerts of the last 24 hours.
        • 

      • Rate limiting, also called throttling: a maximum number of messages per period, such as the Wazuh option email_maxperhour.
        • 

      • Documented suppression: deliberately not notifying a known and approved activity, for example during a maintenance window, an approved period of planned work, with a written reason and an end date.
        • 

      

      Then compare the expected workload with the capacity. At Val-des-Pins, monitoring time is 60 minutes per day (Lesson 2.5). If the review of a High alert takes about 8 minutes, fewer than 8 High alerts fit in one day. When normal days keep exceeding the budget, the rules must be tuned (Lesson 3.5.4 and Topic 6.4), not ignored.
      

      Slide 34
      

      Alerts inform; people decide the actions
      

      Some tools can respond automatically. The active response feature of Wazuh (documentationcheck) can, for example, block an address after an alert. In this course, alerts only notify people. Any blocking or containment action on a real system requires the owner's written approval, a change window and a tested rollback, and automated measures that reach out to, disable or retaliate against another system are prohibited in every course (Legal Notice §7.4).

        Slide 39
        

        Why every alert must be tested
        

        A rule that has never fired may be correct or broken, and you cannot know which without a test. Alert testing is the controlled production of a safe event that should trigger the rule, a positive test, or that should not trigger it, a negative test, followed by the comparison of the expected result with the actual result. Negative tests are as important as positive ones: they prove that the rule is not too broad. Tests are run only in the lab, on the designated systems, with synthetic data (Legal Notice §6.4 and §6.7).
        

        Slide 40
        

        Four outcomes and two ratios
        

        Every test result is one of four outcomes.
        

          

        • True positive (TP (true positive)): an alert was expected and raised.
          • 

        • False positive (FP (false positive)): no alert was expected, but one was raised. False positives waste review time and feed alert fatigue.
          • 

        • False negative (FN (false negative)): an alert was expected, but none was raised. This is the most dangerous outcome, because the team believes that it is protected when it is not.
          • 

        • True negative (TN (true negative)): no alert was expected and none was raised.
          • 

        

        Two ratios summarize a set of tests. Precision = TP (true positive) ÷ (TP (true positive) + FP (false positive)) is the share of raised alerts that were justified. Recall, also called the detection rate, = TP (true positive) ÷ (TP (true positive) + FN (false negative)) is the share of expected detections that were made. A rule set with high precision but low recall raises few alerts but misses real problems; a rule set with high recall but low precision detects the problems but produces more alerts than people can review.
        

        Slide 41
        

        Producing test events safely
        

          

        1. The test utility of the tool. Wazuh provides wazuh-logtestcheck on the manager (/var/ossec/bin/wazuh-logtest) and the dashboard page "Ruleset Test". You paste a sample log line and the tool shows which decoder and which rule match, using the same rules as the analysis engine, without creating a real event (testing decoders and rulescheck). Saving the rule file is enough to test it with wazuh-logtest; the Wazuh manager must be restarted before the rule produces real alerts.
          2. 

        2. A harmless real action on a lab machine. For example, type a wrong password five times on the lab virtual machine that plays PC-ACCT-01, with a test account created for the exercise.
          3. 

        3. A synthetic log line written into a test file that the lab agent reads.
          4. 

        

        Never test on a production system, on a shared network or with the account of a real person. A test that triggers a real alert at a workplace creates a real incident for real people.
        

        Slide 42
        

        Tuning and regression testing
        

        Tuning is the controlled change of a rule to remove false positives or false negatives: narrowing a match condition that is too broad, adding a value that was forgotten (for example logon type 10, used by remote desktop), adjusting a threshold with baseline evidence, or adding a documented exception. After every change, run the whole test plan again, positive and negative tests. This regression testing proves that the correction did not break another detection.
        

        Slide 43
        

        The alert register and version control
        

        Each rule has an entry in the alert register: identifier, version, purpose, data source, condition, severity, notification, response note, test identifiers and results, owner, date of approval and next review date (Table 3.5.G). A rule change is a configuration change: it needs a reason, a test, an approval and a way back to the previous version, called a rollback, the change-management discipline of Class 6. Keep each version of local_rules.xml. Wazuh leaves your custom files in /var/ossec/etc/rules unchanged when it is upgraded, but it replaces the default rule files in /var/ossec/ruleset/rules, so never edit those files.

          Step-by-step explanation
          1. Every line that starts with # is a comment for bash. The option set -eu stops the script at the first error or at any unset variable.
          2. TESTS is the test plan: eleven entries written as identifier|rule|expected result|log lines, with positive and negative tests. The log lines of one test are separated by semicolons, and all of them are synthetic.
          3. rule_match() returns the match condition of each rule and version, written as an extended regular expression. Version 1.0 contains the two faults: AL-05 matches the word cleared, and AL-03 accepts logon type 2 only. Version 1.1 corrects them.
          4. rule_exclude() returns the allowlist of AL-08 (198.51.100.20, the address of the vendor), and rule_min() returns the count needed: 5 for AL-01, 1 for the other rules.
          5. evaluate() splits the batch into lines, counts the lines that match the pattern and are not excluded, and prints ALERT when the count reaches the minimum, otherwise NO_ALERT.
          6. run_plan() runs the whole plan for one version: for each test it compares the expected result with the actual result, classifies the outcome as TP (true positive), FP (false positive), FN (false negative) or TN (true negative), and appends one line to the test record.
          7. awk calculates precision and recall from the four counters.
          8. The plan runs twice. Version 1.0: T06 is a false positive and T08 a false negative, so precision and recall are both 83.3 %. Version 1.1, the regression run: six true positives and five true negatives, 100 %.
          9. The test record class12_alert_test_record_output.csv holds 22 lines of evidence: 11 tests for each of the 2 versions.

          What to remember
          

            

          1. An alert rule is a written condition with seven parts; its type (single event, threshold, baseline deviation, sequence, absence) tells what the tool must remember.
            2. 

          2. Thresholds come from the baseline: one profile per type of hour, the larger of mean + k × standard deviation and a documented floor, checked against the baseline counts.
            3. 

          3. Every alert has a severity, a channel, a recipient, an acknowledgement target and an escalation path, and the total workload must fit the time available.
            4. 

          4. No rule is trusted before positive and negative tests; every change is tuned, tested again, recorded and approved.
            5. 

          5. All of it happens in the lab, with synthetic data, and alerts inform people; they do not act on real systems.

          Table 3.5.H. Terms of the lesson
          TermDefinition
          EventOne recorded occurrence on a system or network (logon, file change, firewall decision).
          Log entryThe stored record of an event, made of fields such as time, host, account and event number.
          Suspicious behaviourAn activity or pattern that does not prove an attack but appears often during attacks.
          Predefined suspicious behaviourA suspicious behaviour that the monitoring team decides in advance to watch and writes down.
          AlertA notification produced when the collected data satisfy the condition of an alert rule.
          Alert rule (detection rule)The written condition that the tool evaluates on incoming events.
          Sliding time windowA window that moves with time: only the events of the last N seconds are counted.
          Grouping keyThe field that must be the same in all the events counted by a rule.
          Single-event ruleA rule that fires on one rare and serious event.
          Threshold (frequency) ruleA rule that fires when a count of matching events inside a window reaches a value.
          Baseline-deviation (anomaly) ruleA rule that compares a measured value with the normal range of the baseline.
          Sequence (correlation) ruleA rule that fires when different events occur in a given order within a window.
          Absence (heartbeat) ruleA rule that fires when an expected event does not arrive.
          ThresholdThe value beyond which the tool raises an alert.
          Static thresholdA fixed number chosen from knowledge or policy.
          Baseline-derived (dynamic) thresholdA threshold calculated from measurements of normal activity.
          MeanThe sum of the values divided by their number.
          Standard deviationA measure of how far the values usually are from the mean (sample formula: divide by n − 1).
          PercentileThe value below which a given percentage of the measurements fall; the 99th percentile is written P99 (99th percentile).
          ProfileA group of hours with similar normal activity, such as office hours and off hours.
          Multiplier kThe number of standard deviations added to the mean to form a candidate threshold.
          Minimum floorAn absolute value below which no alert is raised; a documented business decision.
          SeverityHow serious the possible consequence of the detected behaviour is.
          PriorityThe order of handling; it combines severity, asset importance and time of day.
          Notification channelThe way an alert reaches a person: dashboard, e-mail, text message, phone call, ticket.
          Acknowledgement targetThe maximum time before someone confirms that they are handling an alert.
          EscalationNotifying the next role when an alert is not acknowledged in time.
          Accepted riskA known risk that the owner decides in writing not to reduce further.
          Alert fatigueThe decline in attention and response quality caused by more alerts than people can examine.
          DeduplicationOne notification for repeated identical alerts within a window, with a count.
          Grouping (aggregation)One message for several related alerts, for example a daily digest.
          Rate limiting (throttling)A maximum number of messages per period.
          Documented suppressionDeliberately not notifying a known, approved activity, with a reason and an end date.
          Maintenance windowAn approved period of planned work.
          Positive test / negative testA test event that should / should not trigger the rule.
          True positive, false positive, false negative, true negativeThe four outcomes of a test (expected alert raised; unexpected alert raised; expected alert missed; no alert expected and none raised).
          PrecisionTrue positives divided by all raised alerts (true positives + false positives).
          Recall (detection rate)True positives divided by all expected detections (true positives + false negatives).
          TuningThe controlled change of a rule to remove false positives or false negatives.
          Regression testingRunning the whole test plan again after a change.
          Alert registerThe document that describes every rule, its tests and its life cycle.
          RollbackReturning to the previous version of a configuration.
