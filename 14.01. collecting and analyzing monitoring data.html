4.1 Event logs: Windows and Linux Slides 5–28

4.1.1 What an event log is, and why monitoring depends on it

An event log is a time-ordered file in which an OS (Operating System), its services and its applications record events: discrete, dated occurrences such as "a user logged on", "a service started", "a configuration was changed", "a disk is almost full". Each event record (also called a log entry) contains at least six pieces of information: a timestamp (date and time, ideally with its time zone), the source (which program or component wrote it), an identifier (on Windows a numeric Event ID; on Linux the program name and its PID (Process Identifier)), a severity level (how serious it is), the host that produced it, and a message with the details — typically a user name, a network address and a result.

Why does preventative monitoring depend on logs? Because logs are the primary host-based evidence of activity. The baseline you built in Lab 2 is, in large part, a statistical description of normal events: how many logons per day, at what hours, from which addresses, how many failures are normal. An alert rule is a condition applied to new events. When Topic 5 asks you to diagnose an anomaly, the diagnosis is built from the event records that surround it. If an event was never written, it cannot be found later: completeness of logging is decided before an incident, not after.

Two families of logs coexist on every host. Operational logs describe the health of the system: errors, warnings, service start and stop, driver problems. Audit logs (on Windows the Security log; on Linux the authentication log and the audit framework) describe who did what: logons, use of privileges, changes to accounts and policies. A performance issue (Topic 1.5) shows first in operational logs; a security issue shows first in audit logs; a good technician reads both, because attackers also cause crashes and because disks also fill up for innocent reasons.

4.1.2 Windows event logs

On Windows the Windows Event Log service receives events from every component and stores them in binary files with the EVTX (Windows XML Event Log file) extension, located in C:\Windows\System32\winevt\Logs\. You read them with the graphical Event Viewer (eventvwr.msc), with the command-line tool wevtutil, or with PowerShell. Internally every event is an XML (Extensible Markup Language) document; the Event Viewer only renders it.

The standard channels, grouped under "Windows Logs", are:

  • Application — events written by installed programs (database engines, backup software, antivirus).
  • Security — the audit log: logons, logoffs, use of privileges, account and group changes, policy changes, object access. Only the LSASS (Local Security Authority Subsystem Service) writes here, which is why its content is trusted.
  • System — events written by Windows components: drivers, services, the kernel, the time service, shutdowns and restarts.
  • Setup — installation and update events.
  • Forwarded Events — events received from other machines when forwarding is configured.

Below them, "Applications and Services Logs" contains hundreds of specialised channels, each with up to four sub-logs (Admin, Operational, Analytic, Debug). The ones a monitoring technician meets most are Microsoft-Windows-PowerShell/Operational (which scripts ran), Microsoft-Windows-Windows Defender/Operational (malware detections), Microsoft-Windows-TaskScheduler/Operational (scheduled tasks), Microsoft-Windows-TerminalServices-LocalSessionManager/Operational (remote desktop sessions) and, when the free Microsoft tool Sysmon (System Monitor) is installed, Microsoft-Windows-Sysmon/Operational, which records every process creation with its command line and file hash, every network connection made by a process, and more.

Anatomy of a Windows event

Open any event in Event Viewer and you see the same fields: Level (Critical, Error, Warning, Information, Verbose — the Security log uses the Keywords Audit Success and Audit Failure instead), Date and Time, Source (the provider), Event ID, Task Category, User, Computer and the Description. The "Details" tab shows the XML: a <System> element with the identifiers and the time (always stored in UTC (Coordinated Universal Time), displayed in local time), and an <EventData> element with named fields. Those named fields — TargetUserName, IpAddress, LogonType, SubStatus — are what a script extracts, and what Figure 4.1-B shows side by side with the Linux equivalent.

Nothing is logged unless the audit policy says so

The Security log contains only the categories that the audit policy enables. On a fresh installation several categories are off or record successes only. You configure them with the Local Security Policy console or, in a domain, with a GPO (Group Policy Object) under Advanced Audit Policy Configuration; you verify them with auditpol /get /category:*. Three settings matter most for a small network: Audit Logon (success and failure — produces 4624/4625), Audit Account Management (4720 to 4756), and Audit Process Creation (4688; the command line of the process needs the additional setting "Include command line in process creation events"). Enabling categories increases the volume of events, which is why the next question is always the size of the log.

Reading the log: Event Viewer, wevtutil, PowerShell

In Event Viewer, Filter Current Log accepts a list of event IDs (for example 4625,4740) and a time range. From the command line, wevtutil qe Security /q:"*[System[(EventID=4625)]]" /c:20 /rd:true /f:text prints the last twenty failed logons in text. In PowerShell, Get-WinEvent with a filter hashtable is the modern, fast way: Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddHours(-24)}. The older Get-EventLog exists only in Windows PowerShell 5 and is slow on large logs. To hand the events to a script or a spreadsheet you pipe the result to Export-Csv; the companion script export_security_4625.ps1 of Example 4.1 does exactly that and extracts the four EventData fields.

Size, retention, forwarding

By default each standard log is limited to about 20 MB and, when full, overwrites the oldest events. On a domain controller the Security log can wrap in minutes, which means that a weekend's evidence is gone by Monday. Two measures fix this: increase the maximum size (hundreds of megabytes are normal on servers) and, above all, forward events continuously to a central store. Windows offers WEF (Windows Event Forwarding) with a WEC (Windows Event Collector) server: built-in, agentless, using WinRM (Windows Remote Management); most monitoring tools use an agent instead (the Wazuh agent, Winlogbeat, NXLog, the Splunk forwarder). Forwarding also protects the evidence: an intruder who clears the local log with event 1102 cannot clear the copy that already left the machine — and the 1102 itself is forwarded and raises an alert.

4.1.3 Linux logs

Linux has two logging systems that usually run together. The syslog family — today almost always rsyslog, sometimes syslog-ng — receives messages from programs and the kernel and writes them as plain-text lines in /var/log/. The newer systemd-journald collects the same messages, plus the output of every service managed by systemd, in a binary, indexed journal that you read with journalctl. On Ubuntu and Debian both exist: journald collects and forwards to rsyslog, which writes the files. On recent RHEL-family systems rsyslog is still installed but the journal is the primary store.

The syslog message: facility, severity, PRI

The format of a message is standardized by RFC (Request for Comments) 5424 (the current standard) and RFC 3164 (the older BSD format that many files still use). A message carries a facility — which subsystem produced it: kern, user, mail, daemon, auth, authpriv, cron, local0 to local7 — and a severity from 0 (emergency) to 7 (debug). The two are combined into one number, the PRI (Priority value): PRI = facility × 8 + severity. An authentication message of severity "informational" from facility auth (4) has PRI 4 × 8 + 6 = 38, which is why the modern form of the line in Figure 4.1-B starts with <38>. The rsyslog configuration uses exactly these two values to decide where a message goes: the rule auth,authpriv.* /var/log/auth.log means "every severity of the auth and authpriv facilities to this file".

A classic line, as written in /var/log/auth.log, has four parts: the timestamp (month, day, time — no year and no time zone, a known weakness of RFC 3164 that every parser must compensate), the hostname, the program name and PID in square brackets, and the free-text message. Learning these phrases is the Linux equivalent of learning event IDs.

Reading the logs

The everyday commands: tail -f /var/log/auth.log follows the file live; grep "Failed password" /var/log/auth.log | wc -l counts failures; grep -c sudo /var/log/auth.log counts sudo lines; journalctl -u ssh --since "1 hour ago" shows the SSH service's messages of the last hour; journalctl -p err -b shows errors since the last boot; journalctl -k shows kernel messages; last and lastb list successful and failed logins; logger -p auth.warning "monitoring test" writes a test message that you can then look for in the central tool — the standard way to verify that forwarding works end to end.

Rotation and forwarding

Text logs grow without limit unless logrotate rotates them: its configuration (/etc/logrotate.conf and /etc/logrotate.d/) renames auth.log to auth.log.1, compresses older copies to auth.log.2.gz, and deletes copies beyond the retention count — a weekly rotation with four copies keeps about one month. The journal has its own limit (SystemMaxUse= in /etc/systemd/journald.conf; journalctl --disk-usage shows the current size). Forwarding to the central server is one rsyslog line: *.* @@logsrv.nordik.lan:514 — one @ sends over UDP (User Datagram Protocol) (fast, no delivery guarantee), two @@ send over TCP (Transmission Control Protocol) (reliable, and the base for TLS (Transport Layer Security) encryption). As on Windows, forwarding is also a protection: a copy that has left the host cannot be erased from the host.

4.1.4 Rules that apply to both platforms

  • Time: every host synchronizes with NTP (Network Time Protocol) (Windows: the Windows Time service, w32tm /query /status; Linux: chrony or systemd-timesyncd, timedatectl). Record and compare in UTC (Coordinated Universal Time); Montréal switches between −04:00 and −05:00 twice a year, and a log without a zone is ambiguous one hour per year.
  • Completeness: enable the categories you will need (logon, account management, process creation, sudo) before you need them, and verify with a test event (logger on Linux; a deliberate failed logon on a test account on Windows).
  • Centralization and integrity: forward promptly over a reliable transport, restrict who can read the central store, keep the local logs as a second copy, and alert on the events that mean "someone touched the logs" (1102, 4719, 1100, a stopped rsyslog).
  • Retention: decide how long you keep events online (90 days is a common minimum) and archived (one year or more), according to the organization's needs and to the law; the NIST SP 800-92 guide (NIST (National Institute of Standards and Technology), SP (Special Publication) 800-92, Guide to Computer Security Log Management) is the reference for writing this policy.
  • Privacy: a log line that contains a user name, an address and a time is personal information under Québec's Law 25 and under the Cyber.SoHo Legal Notice, Terms of Use and Acceptable Use Policy (v2.0) (sections 6.7 and 7.2). Collect the minimum that monitoring requires, protect it, never post real logs, and delete what is no longer needed.
  • Volume: a workstation writes a few thousand events a day; a domain controller can write millions. Collect what you can analyze, and let the baseline tell you which counts are normal, so that Topic 5 can tell you which are not.

Real-life example 4.1 — Monday-morning log review at Atelier Nordik inc.

Task performed by the example: determine whether password-guessing activity took place during the weekend against the two servers of a small company, by counting failed logon attempts per source address in the Windows Security log and in the Linux authentication log, and produce one table the team lead can read in thirty seconds.

How it relates to this lecture: it uses the 4625 event and its EventData fields (4.1.2), the auth.log line anatomy and the "Failed password" vocabulary (4.1.3), and the common rules on timestamps and central summaries (4.1.4).

How it feeds Lab 3: the output file logon_failures_summary.csv is the "detection evidence" that Part 3 of the Integrative Project (Lab 3, October 16) starts from; the same script, run on the Lab 3 data set, will give you the sources to diagnose.

The setting. Atelier Nordik inc. is a fictional fourteen-person industrial-design firm in Montréal's Mile-End. Its network is the one mapped in Lab 1: an OPNsense firewall with a LAN (Local Area Network) (192.168.10.0/24) and a DMZ (Demilitarized Zone) (192.168.20.0/24), a Windows server SRV-AD01 (192.168.10.5 — AD DS (Active Directory Domain Services) domain controller and file server), a Linux web server srv-web01 (192.168.20.10, Ubuntu), twelve workstations, a monitoring server (192.168.10.250) running the Lab 2 tool, and a VPN (Virtual Private Network) that gives remote users addresses in 10.8.0.0/24. Nobody works on weekends, except one designer (user ldube) who connected through the VPN on Saturday morning.

What happened. On Monday at 08:05 the monitoring tool shows the alert "logon failures above baseline" for the weekend. The technician — you — exports the 4625 events of the weekend from SRV-AD01 with export_security_4625.ps1, copies /var/log/auth.log from srv-web01, and runs logon_failures.py on both files. The script reads the Windows rows, reads the Linux lines, groups the attempts by (host, source address), measures how many attempts fall inside any ten-minute window, flags a source at ten or more, and writes the summary.

What the summary says — and what it does not. Two sources are flagged: 203.0.113.57, an Internet address that tried twenty-three passwords for seven account names on srv-web01 between 03:14 and 03:18 on Sunday, and 10.8.0.9, a VPN address that tried the administrator password fifteen times on SRV-AD01 at 02:40 on Sunday. The designer's three failures on Saturday and the two local failures are below the threshold and stay "normal". The summary tells you where to look; it does not tell you why. Which VPN account held address 10.8.0.9 at 02:40, whether the Internet address also touched the firewall, whether the administrator account was locked, whether any logon finally succeeded — those are the questions of Lab 3 and of Topic 5, and the raw files you just used are their evidence.

35AUTH_RE = re.compile(

37 r'^(?P<ts>[A-Z][a-z]{2}\s+\d{1,2}\s\d{2}:\d{2}:\d{2})\s'

45def read_windows(path):
46 """Return a list of failure records read from a PowerShell Export-Csv file."""
47 # The list that will receive one record (a small dictionary) per 4625 event.
48 records = []
49 # Open the CSV file; newline='' is the documented way to open CSV files in Python.
50 with open(path, newline='', encoding='utf-8-sig') as f:
51 # DictReader maps every row to a dictionary keyed by the header names.
52 for row in csv.DictReader(f):
53 # Keep only failed logons (4625); the export may contain other IDs.
54 if row['Id'].strip() != '4625':
55 # Skip any other event ID.
56 continue
57 # The export writes TimeCreated in ISO 8601 form, e.g. 2026-10-04T02:40:12.
58 ts = datetime.strptime(row['TimeCreated'].strip(), '%Y-%m-%dT%H:%M:%S')
59 # A dash means "no network address": the logon came from the console or a service.
60 ip = row['IpAddress'].strip() or '-'
61 # Translate the dash into a readable label for the summary table.
62 ip = 'local' if ip in ('-', '::1', '127.0.0.1') else ip
63 # Store the record; the host name is shortened to its first label (SRV-AD01).
64 records.append({'host': row['Computer'].split('.')[0], 'os': 'Windows',
65 'ts': ts, 'user': row['TargetUserName'].strip(), 'ip': ip})
66 # Give the complete list back to the caller.
67 return records

70def read_linux(path, year):
71 """Return a list of failure records read from a syslog-style auth.log file."""
72 # The list of records built from the matching lines.
73 records = []
74 # Open the text log; errors='replace' avoids a crash on a stray non-UTF-8 byte.
75 with open(path, encoding='utf-8', errors='replace') as f:
76 # Read the file line by line (log files can be very large).
77 for line in f:
78 # Try to match the failure pattern; lines that do not match return None.
79 m = AUTH_RE.match(line)
80 # Ignore every line that is not a "Failed password" line (sudo, cron, sessions...).
81 if not m:
82 # Nothing to count on this line.
83 continue
84 # RFC 3164 timestamps carry no year: we add the year given on the command line.
85 ts = datetime.strptime(f"{year} {m.group('ts')}", '%Y %b %d %H:%M:%S')
86 # Build the record with the same keys as the Windows records.
87 records.append({'host': m.group('host'), 'os': 'Linux', 'ts': ts,
88 'user': m.group('user'), 'ip': m.group('ip')})
89 # Return the list of Linux failures.
90 return records

93def check_window(times):
94 """Return the largest number of failures that fall inside any WINDOW_MINUTES window."""
95 # Sort the timestamps so the sliding window can move from oldest to newest.
96 times = sorted(times)
97 # The window length as a timedelta object, comparable with time differences.
98 window = timedelta(minutes=WINDOW_MINUTES)
99 # The best (largest) count found so far.
100 best = 0
101 # 'start' is the index of the oldest event still inside the current window.
102 start = 0
103 # Walk through every event with index 'end' as the newest event of the window.
104 for end in range(len(times)):
105 # Drop old events from the front while the window is longer than allowed.
106 while times[end] - times[start] > window:
107 # Move the start of the window forward by one event.
108 start += 1
109 # The number of events between start and end inclusive is a candidate.
110 best = max(best, end - start + 1)
111 # Return the maximum density observed.
112 return best

115def summarize(records):
116 """Group the records by (host, source ip) and build the summary rows."""
117 # groups[(host, ip)] -> list of records for that pair.
118 groups = defaultdict(list)
119 # Distribute every record into its group.
120 for r in records:
121 # The key combines the target host and the source address.
122 groups[(r['host'], r['ip'])].append(r)
123 # The rows of the final table.
124 rows = []
125 # Build one row per group.
126 for (host, ip), items in groups.items():
127 # All timestamps of this group, used for first/last and the window check.
128 times = [r['ts'] for r in items]
129 # Highest number of failures observed inside one 10-minute window.
130 dense = check_window(times)
131 # Decide the flag: ALERT when the density reaches the threshold.
132 flag = 'ALERT' if dense >= THRESHOLD else 'normal'
133 # Collect the distinct user names tried, in alphabetical order.
134 users = ','.join(sorted({r['user'] for r in items}))
135 # Append the row as a dictionary (same keys as the CSV header below).
136 rows.append({'host': host, 'os': items[0]['os'], 'source_ip': ip,
137 'attempts': len(items), 'first_seen': min(times).isoformat(sep=' '),
138 'last_seen': max(times).isoformat(sep=' '), 'usernames': users,
139 'max_in_10min': dense, 'flag': flag})
140 # Sort: alerts first, then the busiest sources.
141 rows.sort(key=lambda x: (x['flag'] != 'ALERT', -x['attempts']))
142 # Return the ordered rows.
143 return rows

Step-by-step explanation of the code

  1. Imports and constants. csv reads and writes comma-separated files; re compiles the regular expression that recognizes an SSH failure line; datetime computes time differences; defaultdict creates groups on first use. THRESHOLD = 10 and WINDOW_MINUTES = 10 are the only two numbers you will tune in Lab 3 (Topic 6.4: fewer false alarms).
  2. AUTH_RE. One pattern with four named groups — timestamp, host, user, address — that matches only the lines "Failed password for [invalid user] NAME from A.B.C.D". The optional group (?:invalid user )? is what makes the pattern accept both an unknown account and a known account with a wrong password.
  3. read_windows(). Opens the PowerShell export with csv.DictReader, keeps only Id == 4625, parses the ISO 8601 time, and translates the dash of IpAddress into the word local because console and service logons have no network address. Each record is a small dictionary with the same five keys as the Linux records — that is what makes one summary possible for two platforms.
  4. read_linux(). Reads the file line by line, applies the regular expression, ignores every other line (sudo, cron, sessions), and adds the year given on the command line because the RFC 3164 timestamp has none.
  5. check_window(). Sorts the timestamps of one group and slides a window over them: for each event taken as the end of the window, it drops events from the start until the window is ten minutes or less, and remembers the largest number of events seen inside a window. Fifteen attempts in two minutes give 15; three attempts spread over a day give 1.
  6. summarize(). Groups the records by (host, address), computes the first and last time, the sorted set of user names, the window density, and the flag ALERT or normal; then sorts alerts first and busiest sources next.
  7. main(). Reads the arguments, joins the two record lists, writes the CSV with csv.DictWriter, prints the aligned table, and ends with the number of flagged sources. The flag is a detection; the diagnosis belongs to Lab 3.

Export command used on the Windows server (companion file)

The PowerShell script export_security_4625.ps1 — included in the download bundle with a comment before every line — asks the Event Log service for the 4625 events since Friday 18:00 with Get-WinEvent -FilterHashtable, converts each event to XML with ToXml(), picks the TargetUserName, IpAddress, LogonType and SubStatus values from EventData, and writes security_export.csv with Export-Csv -NoTypeInformation.

5# the five fields the monitoring summary needs.
6# RELATION TO THE LECTURE: Get-WinEvent with a filter hashtable (4.1.2), the
7# EventData fields of 4625 (TargetUserName, IpAddress, LogonType, SubStatus).
8# Run in an elevated PowerShell on the Windows server (or a collector).
9# Educational material — Cyber.SoHo Legal Notice:
10# https://cyber-soho.github.io/prevmon/00.01.%20cyber.soho%20-%20legal.html

15
16# Ask the Event Log service for Security events with ID 4625 created after $since.
17# A filter hashtable is evaluated by the service itself, so it is fast even on big logs.
18$events = Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4625; StartTime = $since }

20# Transform every event object into a flat object with named columns.
21$rows = foreach ($e in $events) {
22 # The useful fields live in the XML <EventData> part; ToXml() returns that XML as text.
23 $xml = [xml]$e.ToXml()
24 # Each <Data Name="..."> element becomes a value we can look up by its Name attribute.
25 $data = @{}
26 # Fill the lookup table.
27 foreach ($d in $xml.Event.EventData.Data) { $data[$d.Name] = $d.'#text' }
28 # Produce one output object; TimeCreated is written in ISO 8601 ('s' = sortable) format.
29 [pscustomobject]@{

41$rows | Sort-Object TimeCreated | Export-Csv -NoTypeInformation -Encoding UTF8 .\security_export.csv

4.2.1 What travels on the wire: frames, packets and conversations

Hosts do not send files or web pages; they send small units. An application hands its data to the transport layer, which splits it into TCP (Transmission Control Protocol) segments or UDP (User Datagram Protocol) datagrams and adds a header with a source and a destination port. The network layer wraps each segment in an IP (Internet Protocol) packet whose header carries the source and destination addresses, a protocol number (6 for TCP, 17 for UDP, 1 for ICMP (Internet Control Message Protocol)) and a TTL (Time To Live). The link layer wraps the packet in an Ethernet frame with the source and destination MAC (Media Access Control) addresses. This nesting is called encapsulation (Figure 4.2-A). A protocol analyzer does the reverse: it reads the frame header, then the IP header, then the TCP header, then — if it is not encrypted — the application data.

Figure 4.2-A — Encapsulation: what each header tells a monitor

The header fields a monitor reads

For monitoring, a handful of fields answer most questions: the two IP addresses (which hosts talk — internal to internal, internal to Internet?), the protocol number, the destination port (which service — Table 4.2-A), the TCP flags (SYN (Synchronize flag), ACK (Acknowledgement flag), FIN (Finish flag), RST (Reset flag) — the state of the connection), the frame length and the timestamp. Addresses, ports and the protocol form the 5-tuple (source IP, destination IP, source port, destination port, transport protocol) that identifies one conversation — also called a flow. Every statistic a monitoring tool shows ("top talkers", "conversations", "bytes per host") is computed by grouping packets on some part of the 5-tuple, which is exactly what Example 4.2 does by hand.

The TCP three-way handshake

A TCP connection starts with the three-way handshake: the client sends a segment with the SYN flag, the server answers with SYN and ACK, the client confirms with ACK; then data flows, and FIN or RST ends the connection. This matters for monitoring because the handshake exposes intent and result in three small packets: a SYN answered by SYN-ACK means "the port is open and a session started"; a SYN answered by RST means "the port is closed"; a SYN with no answer at all means "nothing is listening, or a firewall dropped it". One source sending SYNs to many ports of one host, receiving RSTs for most of them, is the signature of a port scan — the pattern of Example 4.2.

What encryption hides, and what it does not

Most traffic today is protected by TLS (Transport Layer Security), and the application data inside it cannot be read by the monitor. Everything around it still can: the addresses, the ports, the number and size of packets, their timing, and — in most connections — the SNI (Server Name Indication) field of the first TLS message, which names the server the client wants (for example updates.vendor.example). Monitoring therefore remains possible with encrypted traffic: who talks to whom, how much, how often and when are precisely the values that a baseline describes and that an anomaly violates.

4.2.2 What a packet capture is, and where to take it

A packet capture copies every frame that a network interface sees, adds a timestamp to each, and stores them in memory or in a file in the pcap (packet capture file format) or pcapng (packet capture next generation file format) format. The copying is done by a capture library — libpcap on Linux and macOS, Npcap on Windows — and the tools (Wireshark, tcpdump) sit on top of it. To see frames that are not addressed to it, the NIC (Network Interface Card) is put in promiscuous mode. That mode, however, only shows what reaches the interface, and on a modern switched network a switch forwards a unicast frame only to the port of its destination MAC address. A workstation in promiscuous mode therefore still sees only its own traffic plus broadcasts; to observe other hosts you must bring their traffic to your interface.

The four capture points

Figure 4.2-B places the four options on the Atelier Nordik network. (1) On the host under study: quickest, complete for that host, but it modifies the machine you are examining and is not possible on an appliance. (2) On a SPAN (Switched Port Analyzer) or mirror port: the switch copies the frames of selected ports or VLAN (Virtual Local Area Network)s to the port where the monitoring server listens — the usual choice in a small office, with one limit: a saturated switch may drop mirrored frames. (3) With a hardware TAP (Test Access Point): a passive device inserted inline, typically on the link to the Internet, that gives an exact copy and cannot be disabled by software. (4) On the firewall: OPNsense and pfSense include a packet-capture page that records what crosses the gateway — everything between LAN, DMZ and the Internet, nothing that stays inside one switch. The rule from Chris Greer's lesson applies: capture as close as possible to the host you investigate, and avoid installing tools on a busy production server.

Figure 4.2-B — Four capture points on the Atelier Nordik network

Full capture, flow records, metadata

A full capture of a busy link is large: a 100 Mbit/s link fully used produces about 12.5 MB per second, roughly 45 GB per hour. Small networks therefore do not capture everything all the time. They keep flow records (NetFlow, IPFIX (Internet Protocol Flow Information Export), sFlow — one record per conversation: who, with whom, which port, how many bytes, when), or network metadata produced by a sensor (Zeek writes conn.log, dns.log, ssl.log; Suricata writes eve.json), and they run a full capture on demand, limited by a filter and by a ring buffer (dumpcap -b filesize:102400 -b files:20 keeps twenty files of 100 MB and recycles the oldest). Lab 2's tool most likely keeps flows or metadata; Example 4.2 adds a five-minute full capture for one host.

4.2.3 Filters: capture filters versus display filters

Two kinds of filters exist and students confuse them constantly. A capture filter is written in BPF (Berkeley Packet Filter) syntax, is applied by the capture library before frames are stored, reduces the volume, and cannot be undone: what it excluded was never recorded. Examples: host 192.168.10.44, net 192.168.20.0/24, port 53, tcp port 443, not port 22 (exclude your own SSH session), src host 192.168.10.44 and not port 443. A display filter uses Wireshark's own syntax, is applied to frames already captured, and can be changed as often as you like: ip.addr == 192.168.10.44, tcp.port == 445, dns, http.request, tcp.flags.syn == 1 && tcp.flags.ack == 0 (connection attempts only), tcp.flags.reset == 1, tls.handshake.extensions_server_name contains "update". Reading a capture for monitoring

Open the conversations table and ask the baseline's questions. Who are the top talkers, and are they the servers you expect? Which protocols are present, and is any of them forbidden by policy (Telnet, SMBv1, clear-text FTP)? Does any host attempt connections that are never answered (SYN without SYN-ACK)? Does one source reach many ports of one host in a short time (scan), or many hosts on one port (sweep)? Does any workstation connect at regular intervals to the same outside address (beaconing, typical of malware calling home)? Does any host send far more data out than in (possible exfiltration)? Are there DNS queries for names nobody typed? Each "yes" is an anomaly candidate for Topic 5.

Legal and privacy limits of capture

A capture records other people's communications. Capturing on a shared network you do not own — a residence, a campus, a coffee shop — without authorization is interception under section 184 of the Criminal Code; capturing on your employer's network without a written mandate is unauthorized use under section 342.1. Section 7.2 of the Cyber.SoHo Legal Notice, Terms of Use and Acceptable Use Policy (v2.0) is explicit: capture only on systems you own or on Designated Targets, never enable promiscuous or monitor mode on a shared network, treat every capture as personal information, keep it in the lab, and delete it when the exercise is marked. In this course all captures are produced inside the lab environment on fictional data; Example 4.2 uses a synthetic packet list for exactly that reason.

80 conv = OrderedDict()
81 # Examine every packet once.
82 for p in packets:
83 # Key for the case "this packet goes from the initiator to the responder".
84 forward = (p['src'], p['dst'], p['proto'], p['dport'])
85 # Key for the case "this packet is the responder's answer" (ports swapped).
86 reverse = (p['dst'], p['src'], p['proto'], p['sport'])
87 # If the reverse key already exists, this packet is a reply inside a known conversation.
88 if reverse in conv:
89 # Count it as an incoming packet of that conversation.
90 c = conv[reverse]
91 # Replies increase the incoming counters.
92 c['packets_in'] += 1
93 # Bytes are counted in both directions.
94 c['bytes'] += p['len']
95 # A SYN+ACK reply proves the port is open; a RST reply proves it is closed.
96 c['synack_in'] += int(p['syn'] and p['ack'])
97 # Count resets separately: many RSTs are typical of a scan of closed ports.
98 c['rst_in'] += int(p['rst'])
99 # Update the time of the last packet seen.
100 c['last'] = p['t']
101 # Done with this packet.
102 continue
103 # Otherwise it is an outgoing packet: create the conversation if it is new.
104 if forward not in conv:
105 # A fresh record with all counters at zero and the first timestamp.
106 conv[forward] = {'src': p['src'], 'dst': p['dst'], 'proto': p['proto'],
107 'dport': p['dport'], 'packets_out': 0, 'packets_in': 0,
108 'bytes': 0, 'syn_out': 0, 'synack_in': 0, 'rst_in': 0,
109 'first': p['t'], 'last': p['t']}
110 # The record to update.
111 c = conv[forward]
112 # One more packet sent by the initiator.
113 c['packets_out'] += 1
114 # Add its size.
115 c['bytes'] += p['len']
116 # A SYN without ACK is a connection attempt.
117 c['syn_out'] += int(p['syn'] and not p['ack'])
118 # Keep the last timestamp current.
119 c['last'] = p['t']
120 # Return the conversations as a list, in the order they started.
121 return list(conv.values())

124def detect(convs):
125 """Attach a 'flag' to every conversation and return the list of alerts."""
126 # alerts: human-readable lines printed at the end.
127 alerts = []
128 # ports_by_pair[(src, dst)] -> list of (first_time, dport) to measure the scan density.
129 ports_by_pair = {}
130 # First pass: collect the distinct destination ports per (source, destination) pair.
131 for c in convs:
132 # Default flag: nothing special.
133 c['flag'] = ''
134 # Record the start time and the port of this conversation under its pair.
135 ports_by_pair.setdefault((c['src'], c['dst']), []).append((c['first'], c['dport']))
136 # A conversation with attempts but no answer at all is a NO-REPLY case.
137 if c['syn_out'] > 0 and c['packets_in'] == 0:
138 # Note whether the destination is outside the company: more suspicious.
139 where = 'external' if not is_internal(c['dst']) else 'internal'
140 # Set the flag on the conversation.
141 c['flag'] = 'NO-REPLY'
142 # Describe the finding for the alert list.
143 alerts.append(f"NO-REPLY: {c['src']} sent {c['syn_out']} SYN to {c['dst']}:{c['dport']} ({where}) and got no answer")
144 # Second pass: scan detection per (source, destination) pair.
145 for (src, dst), items in ports_by_pair.items():
146 # Sort the (time, port) tuples by time to apply the 60-second window.
147 items.sort()
148 # Slide a window over the list and count distinct ports inside it.
149 for i in range(len(items)):
150 # Ports of the conversations that started within SCAN_SECONDS after items[i].
151 window_ports = {port for (t, port) in items if 0 <= t - items[i][0] <= SCAN_SECONDS}
152 # Enough distinct ports inside one window: this is a scan pattern.
153 if len(window_ports) >= SCAN_PORTS:
154 # Mark every conversation of this pair.
155 for c in convs:
156 # Match on the source and destination addresses.
157 if c['src'] == src and c['dst'] == dst:
158 # Keep an existing NO-REPLY flag visible as well.
159 c['flag'] = (c['flag'] + ' ' if c['flag'] else '') + 'PORT-SCAN-PATTERN'
160 # One alert line per pair is enough.
161 alerts.append(f"PORT-SCAN-PATTERN: {src} reached {len(window_ports)} distinct ports of {dst} within {SCAN_SECONDS} s")
162 # Stop sliding: the pair is already reported.
163 break
164 # Return the alert lines.
165 return alerts

Step-by-step explanation of the code

  1. Constants. SCAN_PORTS = 10 and SCAN_SECONDS = 60 define the scan pattern (ten distinct ports of one host within one minute); INTERNAL_PREFIXES says which addresses are "inside"; PROTO_NAMES translates the IP protocol number into TCP, UDP or ICMP.
  2. is_true(). tshark prints boolean fields as 1/0 in older versions and True/False in newer ones; this small function makes the script work with both.
  3. read_packets(). Reads the CSV with csv.DictReader, takes the port from the TCP or the UDP column (whichever is filled), converts the flags with is_true(), the length to an integer and the epoch time to a float, then sorts by time.
  4. build_conversations(). For every packet it builds two keys: the forward key (source, destination, protocol, destination port) and the reverse key (destination, source, protocol, source port). If the reverse key already exists, the packet is a reply to a known conversation: it increments packets_in, synack_in if SYN and ACK are set, rst_in if RST is set. Otherwise it is an outgoing packet: the conversation is created if needed, packets_out grows, and a SYN without ACK increments syn_out. Because the client's packet always comes first, both directions end up in one record — the same thing Wireshark does in Statistics → Conversations.
  5. detect(). First pass: a conversation with attempts (syn_out > 0) and no incoming packet at all gets NO-REPLY, and the alert says whether the destination is internal or external. Second pass: for each (source, destination) pair it collects (start time, port) of every conversation, slides a sixty-second window, counts the distinct ports inside it, and marks the whole pair PORT-SCAN-PATTERN when the count reaches ten.
  6. main(). Writes the CSV with readable times (fmt()), prints the aligned table and the alert lines, and ends with the count of packets and conversations. As in Example 4.1, the flags are detections; the pcap opened in Wireshark is where Lab 3's diagnosis continues.

What is the difference between a capture filter and a display filter?
Answer
A capture filter (BPF syntax) decides what is recorded, is set before the capture and cannot be undone. A display filter (Wireshark syntax) selects what is shown from an existing capture and can be changed at any time.
Card 2 · question
Why does a workstation on a switch not see other hosts' traffic, even in promiscuous mode?
Answer
A switch forwards a unicast frame only to the port of its destination MAC address. To see other hosts you need a SPAN/mirror port, a TAP, or a capture on the firewall.
Card 3 · question
Name the five values of the 5-tuple that identify one conversation.
Answer
Source IP, destination IP, source port, destination port, transport protocol (TCP or UDP).
Card 4 · question
Which flags appear in the TCP three-way handshake, in which order, and what does a RST answer to a SYN mean?
Answer
SYN → SYN-ACK → ACK. A RST in answer to a SYN means the port is closed; no answer at all means nothing listens or a firewall dropped the packet.
Card 5 · question
Which Windows built-in tool captures packets without installing Wireshark, and which command converts its output?
Answer
Pktmon (Packet Monitor): pktmon start --capture, then pktmon etl2pcap file.etl -o file.pcapng.
