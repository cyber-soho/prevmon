Topic 3

Lesson 3.1 — Categories of monitoring tools

3.1.1 What a monitoring tool is

A monitoring tool is a program, a device or a service that collects observations about a computer, a network device or a service, stores those observations for a defined retention period (90 days at Val-des-Pins), and evaluates or presents them. These three functions (collection, storage, evaluation with presentation) are the first thing to identify in any product: a syslog server that only collects and stores is still a monitoring tool; a dashboard that evaluates nothing it has not stored is useless on its own.

A tool is built from up to four components:

  • an agent — a program installed on the monitored computer that reads local data (event logs, processes, files) and sends it to a central server;
  • a sensor (also called a probe) — a device or program that reads network traffic from outside the computers, fed by a SPAN (Switched Port Analyzer) port or a TAP (Test Access Point); nothing is installed on the target;
  • a collector — the part that receives data from agents and sensors, or polls devices, and writes to storage;
  • a console (also called the manager, server or dashboard) — the part a person uses to search, visualize and receive alerts.

The expression agent-based or agentless describes the first two components only: agent-based tools install software on the observed machine; agentless tools observe from outside through syslog, SNMP (Simple Network Management Protocol), a SPAN port or an API (Application Programming Interface).

3.1.2 The five kinds of evidence

Categories exist because each tool observes one kind of evidence, and the kinds differ in nature, in volume and in what they can prove.

Evidence What it is Typical source
Event A record that something happened at a given moment (a logon, a service stopped, a firewall rule changed) Windows Event Log, syslog, cloud audit log, firewall connection log
Metric A value sampled at a regular interval (processor load, free disk, bytes per second, ping answered) SNMP counters, ICMP (Internet Control Message Protocol) echo, agent inventory
Flow record A summary of one conversation: addresses, protocol, ports, start time, packets and bytes, no content NetFlow, IPFIX (IP Flow Information Export, RFC 7011), sFlow
Packet The complete transmitted unit, content included when it is not encrypted Capture on a SPAN port or TAP
State Configuration, installed versions or known weaknesses at one moment Vulnerability scan, configuration assessment

A useful reading cue: a firewall's "connection log" is a list of events; "bytes per second on port 3" is a metric.

3.1.3 The seven categories

The first five categories observe the five kinds of evidence; two more collect no new evidence: intrusion detection examines evidence for attack patterns, and the SIEM (Security Information and Event Management) platform combines everything.

Code Category Evidence Examples (open-source; commercial) Key limit to remember

Logs contain only what the audit policy records; a compromised host can clear its local log; every device needs correct time from NTP (Network Time Protocol).
C2 Network traffic capture and analysis Packets and flow records Wireshark, tcpdump, ntopng, nfdump Full capture is expensive (a 100 Mb/s link busy 20 % ≈ 216 GB per day); TLS (Transport Layer Security) hides content; capturing on a shared network is interception.

Two mechanisms that students confuse: a SPAN port (mirror port) is a switch port configured to receive a copy of the frames of selected ports or VLANs (Virtual Local Area Networks); a network TAP is a hardware device inserted into a cable that passes a copy to the sensor without depending on the switch. SNMP polling is pull (the server asks); an SNMP trap is push (the device reports a link down on its own). Standard SNMP ports: polling on UDP (User Datagram Protocol) 161, traps on UDP 162. Syslog travels historically on UDP 514 and, with TLS, on TCP (Transmission Control Protocol) 6514 (RFC 5424).

3.1.4 Six ways to classify any tool

Categories say what a tool observes; the six axes say how it works, with consequences for cost, network load, privacy and skills.

  1. Agent-based / agentless — software on the machine sees inside; agentless observes from outside (the only option for CNC-PC-01).
  2. Passive / active — passive receives logs or a copy of traffic and adds no packets; active sends pings, SNMP polls or scans, creates load and is recorded in the target's logs.
  3. Continuous / scheduled — always on (detection delay of seconds to minutes) versus state at set times.
  4. Signature-based / baseline-based — known patterns versus deviation from measured normal.
  5. Open-source / commercial — published code and no licence cost versus licensing per device or data volume with vendor support.
  6. On-premises / cloud (SaaS, Software as a Service) — data stays inside versus data leaves the site on a subscription.

Wireshark, for example, is agentless, passive, continuous, open-source and on-premises; a vulnerability scanner is active and scheduled; a cloud SIEM is SaaS and commercial.

3.1.5 How the categories combine: the coverage map

A need is covered when at least one category observes the evidence it requires; a plan is covered when every included need is. The coverage map lists assets in rows and categories in columns, with a mark where a need is served. Two consequences: a critical asset should be observed by two independent categories (the file server's event log in C1 and the switch's flow records in C2) so that the failure or compromise of one source does not blind the technician; and one machine can host several categories (MON-01 is at once log collector, availability poller, network sensor and SIEM console). "Categories are functions, not boxes."

At Val-des-Pins, 23 needs on eight assets used five categories (C1, C3, C5, C2, C4); the Tier 1 assets needed C1 + C3 + C5, which is why the first tool had to collect logs, poll availability and manage endpoint agents. The one gap was CNC-PC-01: its logon events would need an agent, which the vendor contract forbids; it is observed agentlessly through FW-01's connection records. A documented gap is a decision; an undocumented gap is a blind spot.

Topic 3

Lesson 3.2 — Selecting the right tool for a given need

3.2.1 The need comes first

A tool is selected to satisfy a stated need; a need is never rewritten to fit a tool that someone already likes. A testable need has six elements: the asset, the evidence (event, metric, flow record, packet or state), the behaviour to detect, the acceptable delay, the recipient of the alert and the retention of the data. Need N-01 of Val-des-Pins is the model: collect the security event logs of FW-01, SRV-FILE-01, PC-ACCT-01 and SW-01, keep them 90 days within 200 GB (gigabytes), and alert the technician by e-mail within 5 minutes when one of the predefined suspicious behaviours occurs. Every word of it can be verified in a pilot.

Two distinctions decide the whole method. A requirement is imposed ("reads Windows event logs"); a preference is a wish ("a dark-themed dashboard"): requirements decide, preferences only break ties. A knock-out criterion (must-have) removes a candidate whatever its other qualities; a weighted criterion can be satisfied more or less and is scored. Confusing the two produces a spreadsheet in which an excellent but unaffordable product wins.

3.2.2 The constraints that filter the list

The constraints of Topic 2 become filters: budget and licence (community editions often cap data volume or device count — verify on the publisher's site), people and skills (one part-time technician, 60 minutes per day: a platform that needs two hours of daily care will stop being used), hardware capacity (one lab VM (Virtual Machine) with 8 GB of RAM (Random-Access Memory) and 200 GB of disk), network impact, operating systems and sources to be read, contracts (CNC-PC-01 agentless), law and privacy (data minimization, retention limit, every capture is personal information), documentation and support, maintenance effort, and exit (no lock-in; data exportable). For a 22-person company the constraint that eliminates the most products is the technician's time.

3.2.3 The selection procedure in seven steps

  1. State the need (six elements).
  2. List the constraints.
  3. Long list — four to eight candidates from the category the need requires ("a need for events is not served by a packet analyzer, however good").
  4. Knock-out filter — verify each must-have from the publisher's documentation, not from marketing pages; one failure removes the candidate and the reason is written; survivors form the short list.
  5. Weighted scoring — fix the criteria and their weights summing to 100 before looking at any candidate; score each short-listed candidate 0 to 5 per criterion with one sentence of justification; total = Σ(weight × score) ÷ 5, a percentage. Fixing the weights first prevents the most common bias: adjusting weights until the preferred product wins. The value of the decision matrix lies in the written justifications more than in the arithmetic.
  6. Pilot — a time-boxed installation in the Authorized Lab Environment that measures what the need states (installation time, memory and disk per day, whether each predefined suspicious behaviour raises an alert within the stated delay); snapshot before, rollback ready.
  7. Decision record — one page: need, constraints, candidates, knock-outs and reasons, scores, choice, alternatives rejected and why, date and review date. It is the starting point of Lesson 6.5.

In the Val-des-Pins matrix for N-01 the knock-outs were K1 (category C1/C7), K2 (zero licence cost), K3 (documented minimum RAM fits 8 GB) and K4 (can send an e-mail alert); the weights were W1 fit 25, W2 ease 20, W3 resources 15, W4 documentation 10, W5 maintenance 10, W6 coverage 10, W7 growth 10. Security Onion failed K3 (minimum 16 GB), Zabbix failed K1 (category C3), Wireshark failed K1 and K4, the cloud SIEM failed K2. Wazuh scored 89.0 % and Graylog Open 69.0 %; Wazuh was piloted with Graylog Open as runner-up, review date October 16.

3.2.4 Frequent selection errors

Choosing by popularity; resource mismatch discovered in the pilot instead of at the knock-out step; ignoring licence terms (section 6.6 of the Legal Notice makes licence compliance your responsibility); forgetting the technician's time for the ninety days after installation; collecting more than the need (full packet capture "because it is more complete"); no rollback (a pilot without a snapshot turns a failed test into a broken lab); wrong category; no decision record.

Topic 3

Lesson 3.3 — Installing monitoring tools and applying updates

3.3.1 Installation is a procedure, not a download

A monitoring tool receives a copy of what happens on every system it watches. Three things can go wrong at once when it is installed carelessly: a tampered copy that sends your data elsewhere; a configuration that misses the events you decided to watch; and a tool that consumes the disk, memory and processor of the lab VM until nothing else works. A procedure is a fixed sequence of stages, each with a check, that produces the same result every time: the word to remember is repeatable. The seven stages are prepare, obtain, verify, install, check, harden, record; the three most often skipped are preparing (nobody checks the memory), verifying (nobody compares the checksum) and recording (nobody writes down what was done).

3.3.2 Before installing

  • System requirements — the minimum processor, memory, disk and operating system versions the publisher tested with. Wazuh all-in-one for 1 to 25 endpoints: 4 virtual processors, 8 GB of memory, 50 GB of disk for 90 days of searchable alerts; MON-01 (4 vCPU (virtual Central Processing Unit) / 8 GB / 200 GB, Ubuntu Server 24.04 LTS (Long-Term Support), five years of security updates) passes. First row of the record: "required 4 / 8 / 50, available 4 / 8 / 200, pass".
  • Official source — the publisher's own website or package repository, never a mirror found through an advertisement, a forum or a video description; note the exact version ("the latest" is not a version).
  • Integrity verification — a checksum is a fixed-length number computed from the entire content of a file with a hash function; SHA-256 (Secure Hash Algorithm, 256-bit) gives 64 hexadecimal characters and changes completely when a single byte changes. A mismatch means the file is corrupted or tampered: delete it and download it again from the official source; never install it. A digital signature is a checksum signed with the publisher's private key and verified with the public key (typically GPG, GNU Privacy Guard); it proves origin and integrity at once. Package repositories do this automatically once the signing key is installed.
  • Snapshot of the VM, named with date and reason ("MON-01 pre-install 4.14.7"), and a change record (what, on which host, when, by whom, the way back).
  • Also on the checklist: network isolation (host-only lab network, no bridge to home or campus) and time synchronised by NTP on MON-01 and the monitored VMs (correlation needs one clock).

3.3.3 Installing the server and connecting the sources

Wazuh has three central components and one agent: the manager (receives events, decodes them, matches rules, produces alerts), the indexer (stores alerts and makes them searchable) and the dashboard (web interface); the agent reads local logs, checks file integrity, inventories the system and sends results over an encrypted channel. All three central components on MON-01 form an all-in-one installation. The installation assistant adds the official repository, imports the signing key, installs the components, generates certificates, starts services and prints the initial administrator password; the documentation recommends disabling the package repository afterwards so that an ordinary OS update cannot upgrade the platform by accident.

Port / protocol Who connects Purpose

1514/TCP enrolled agents Events from the agent to the manager, encrypted with the agent key
514/UDP FW-01, SW-01, NAS-01 Syslog from devices that cannot run an agent (no encryption: acceptable in the isolated lab only)

Sources are connected in the Topic 2 priority order; two hosts get an agent (PC-ACCT-01, SRV-FILE-01), three devices send syslog, and CNC-PC-01 is recorded as "no agent, connection records taken from FW-01".

3.3.4 Checking and hardening

The check rests on four pieces of evidence: the three services are "active"; the dashboard answers on 443 and accepts the administrator login; every enrolled agent is "active" with the installed version; and the first events arrive (a test logon on PC-ACCT-01 appears within a minute; a syslog message from FW-01 appears in the search). A server that runs and monitors nothing is worse than no server, because it gives false confidence.

Hardening means making the fresh installation harder to misuse: replace the generated passwords and store them in a password manager; create a named read-only account for daily checks (least privilege: the daily account must not be able to delete rules or agents); record the self-signed certificate warning and plan a proper certificate; disable the package repository. The CIS Benchmarks give the longer list for the operating system underneath.

3.3.5 Applying updates and rolling back

Three kinds of updates: a software update (major . minor . patch, semantic versioning — semver.org: 4.14.7 → 4.14.8 is a patch, fixes only; 4.14 → 4.15 a minor with new features; 4.x → 5.0 a major with possibly incompatible changes); a content update (rules, decoders, lists — issued often, sometimes weekly, because attacks change faster than software); and an operating system update of the server. The monitoring server is a high-value target: it holds copies of everyone's logs and has a network path to every monitored host. A public weakness gets a CVE (Common Vulnerabilities and Exposures) identifier at cve.org, a score in the NVD (National Vulnerability Database) and, when exploited, an entry in the CISA KEV (Cybersecurity and Infrastructure Security Agency, Known Exploited Vulnerabilities) catalogue. Patching is the second of the ten priority actions of the Canadian Centre for Cyber Security (ITSM.10.096); NIST SP 800-40 Rev. 4 describes patch management as a planned, recurring activity.

The update cycle: read the release notes; plan a maintenance window agreed with the owner (Val-des-Pins: Sunday morning, workshop closed) and take a snapshot; test on a copy if available; apply in the fixed order manager first, agents next, detection content last — an agent must never run a newer version than its manager, because the manager may not understand what a newer agent sends; verify each component (version, status, events still arriving); record. Rollback returns a component to its state before the change (restore the snapshot for the whole server; re-install the previous package for one agent), immediately, before the next host is touched, with a ticket. Two rules: no agent newer than its manager; no change without a tested way back. In the pilot, PC-ACCT-01's agent failed verification after the 4.14.8 push (still 4.14.7, "disconnected" for more than five minutes), was rolled back and ticket 2026-0411 was opened; the record closed at 33 rows and is the Lab 2 deliverable (Section 4, Installation and Update Record).

Topic 3

Lesson 3.4 — Creating the reference database (baseline of normal activity)

3.4.1 Why detection depends on a baseline

"Is 35 logons at 22:00 a problem?" It is alarming in a woodworking shop that closes at five and unremarkable in a hospital; the tool cannot know which, so somebody has to measure normal and write it down. A baseline (the course outline says reference database) is a documented description of the normal activity of a system, a network or an account, measured over a representative period and stored with enough detail to compare new activity against it. It is the basis of anomaly-based detection: an anomaly is activity that departs from the baseline by more than an agreed margin. NIST SP 800-94 describes profiles of normal behaviour built over a training period; NIST SP 800-92 notes that log analysis is only as good as the understanding of what logs normally contain. A baseline is created once and then maintained: a new employee, a new server or a new backup schedule moves the line of normal, and an unreviewed baseline drifts in both directions. The Baseline Record carries a version number, a date and a review date from day one.

3.4.3 How to build one: period, buckets, statistics

The nine-step method: choose the metric and the source from the monitoring plan; fix the observation period (also learning period) of at least two full weeks — most organizations live on a weekly cycle, a shorter period never sees a weekend, and a single week has only one Monday, so nothing can be compared; collect without changing anything on the system; define time buckets (sets of hours expected to behave the same way — the pilot used 24 weekday-hour buckets of 10 values each plus one pooled weekend bucket of 96 values, more reliable than forty-eight tiny ones); compute three statistics per bucket; clean; review with the owner; write and sign the record.

The three statistics: the mean (average); the standard deviation σ (how far values spread around the mean: small means predictable, large means variable; for a bell-shaped distribution about 95 % of values lie within 2σ and about 99.7 % within 3σ); and the 95th percentile p95 (the value below which 95 % of observations fall, not pulled up by one extreme value). The weekday 09:00 bucket of SRV-FILE-01: 10 values, mean 15.2, σ 1.66, p95 17 — "about fifteen logons, rarely more than seventeen". An always-zero hour has σ = 0, so the pilot applies a floor of 1 to σ before computing any boundary. Candidate thresholds: warning = mean + 2σ, alert = mean + 3σ, both rounded up.

3.4.4 Cleaning, validating, documenting

If an intruder, a contractor's test or a misconfigured backup was active during the learning period, the baseline learns it as normal: a polluted baseline, "the single most expensive mistake in this lesson, because it is invisible: the tool works, the numbers exist, and the alarm simply never rings." Defence: test the learning data against itself, comparing each hour with the other values of its bucket while leaving the hour under test out (leave-one-out); otherwise a value of 35 in a bucket of zeros and ones would raise its own bucket's mean and σ enough to hide itself (masking). Any hour above the mean + 3σ of its peers is listed as suspicious and brought to the owner review, "a conversation, not a calculation": each flagged hour receives a decision with a reason. In the pilot, Tuesday September 22 at 22:00 (35 logons) and 23:00 (20) were a documented migration test and were excluded; Friday September 25 at 15:00 (16) was a busy afternoon and was kept. After exclusion, the weekday 22:00 bucket fell from mean 3.7 / σ 10.4 to mean 0.22 / σ 0.42, and its alert boundary from 36 logons to 4 — the next migration test at ten in the evening will be noticed.

The Baseline Record (identifier BL-SRVFILE01-LOGONS-v1.0) lists the period, the observations kept and excluded with a reason for each exclusion, the bucket definition, the statistics per bucket, the candidate thresholds, who reviewed, who approved, the date and the next review (October 16, where it becomes v1.1). Sign-off by the system owner is the last step. The FIM part lists files with their SHA-256 values and the rule that a difference is legitimate only when it corresponds to a change request. Two practical warnings: every baseline and log record is personal information (Legal Notice section 7.2); and build from data the tool collected, never from belief — if the backup service logs on at 02:00 while the schedule says 01:00, the difference is a finding.

Topic 3

Lesson 3.5 — Configuring alerts for suspicious behaviours

3.5.1 From events to alerts: the parts of an alert rule

An event is one recorded occurrence, stored as a log entry made of fields. A suspicious behaviour is an activity, or a pattern of activities, that does not prove an attack but appears often during attacks; the ones the team decides in advance to watch are the predefined suspicious behaviours (criterion 3.2). An alert is a notification produced when the collected data satisfy a written condition, the alert rule (or detection rule). "An alert is a request for human attention, not a verdict."

Every rule is written with seven parts: (1) the data source; (2) the match condition (for example Windows event 4625); (3) the count and time window (5 within 120 seconds, a sliding window that moves with time); (4) the grouping key (the field that must be the same in all counted events — without it, one failure from each of five employees would count as one burst); (5) the severity; (6) the notification; (7) the response note (the first checks, written in advance).

Five types of rules, defined by what the tool must remember: single-event (remembers nothing; event 1102 "the audit log was cleared"); threshold or frequency (remembers the recent matching events; 5 × 4625 within 120 s); baseline-deviation or anomaly (remembers the statistics of the baseline; outbound megabytes per hour); sequence or correlation (remembers that the first event happened; a 4624 success within 10 minutes after a burst of failures); absence or heartbeat (remembers the time of the last event of each source; FW-01 silent for 15 minutes — a missing log can be a technical fault or an attempt to hide activity; in both cases visibility is lost).

Suspicious behaviours come from three sources: the monitoring plan of Lab 1, a public catalogue of attacker techniques — MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge), for example T1110.001 Password Guessing and T1070.001 Clear Windows Event Logs — and the documentation of the monitored systems (Microsoft documents event 4625, 4624, 4732 and 1102). The NIST Cybersecurity Framework 2.0 outcome DE.AE-06 says that information on adverse events is provided to authorized staff and tools.

Before touching any configuration file, each rule is written as a tool-independent rule card. In Wazuh 4.x, custom rules are XML (Extensible Markup Language) in /var/ossec/etc/rules/local_rules.xml with identifiers between 100000 and 120000 (rules syntax); the card maps to the options level (0 to 16), frequency and timeframe, same_field or same_srcip, if_matched_sid, time and weekday, ignore (seconds of silence after firing) and description. Wazuh rules compare fields; they do not calculate averages.

The Val-des-Pins catalogue has nine alerts: AL-01 repeated failed logons (threshold, High), AL-02 success after failures (sequence, Critical), AL-03 interactive or remote logon outside office hours on PC-ACCT-01 (single event with a time condition, logon types 2 or 10, Medium), AL-04 account added to Administrators (event 4732, High), AL-05 Security log cleared (event 1102, Critical), AL-06 mass file changes (FIM threshold, Critical), AL-07 unusual outbound volume (baseline deviation, High), AL-08 CNC-PC-01 contacts a destination not on the vendor allowlist (High), AL-09 log source silent (absence, High).

3.5.2 Thresholds calculated from the baseline

A threshold that is too low turns normal activity into false positives; one that is too high lets real problems pass (false negatives). A static threshold is a fixed number from knowledge or policy (5 failed logons in 120 seconds), suited to quantities whose normal value is near zero; a baseline-derived (dynamic) threshold is calculated from measurements, suited to quantities that change with the hour and the day. Three statistics are used: the mean; the standard deviation (sample formula, division by n − 1); and the percentile (P99 is the value that 99 % of measurements do not exceed; nearest-rank method: sort the n values and take rank ⌈0.99 × n⌉). For a bell-shaped distribution, mean + 3σ is exceeded by about 0.13 % of normal hours, but monitoring data are often not bell-shaped, so the statistical threshold is always compared with the percentile and with the real counts.

Profiles give one threshold per type of hour: Val-des-Pins uses office hours (Monday to Friday, 07:00 to 18:00) and off hours; a single threshold would be too high for the night and too low for the day. Two decisions complete the threshold: the multiplier k in mean + k × σ (a larger k means fewer false positives and more false negatives; choose k by counting how many baseline hours exceed each candidate, which gives the expected false alarms per week), and the minimum floor, an absolute value below which no alert is raised even when the value is statistically unusual — 25 MB per hour at Val-des-Pins, "a documented business decision, not a statistical result". Threshold of a profile = the larger of (mean + k × σ) and the floor.

The AL-07 sheet for PC-ACCT-01 (14 days = 336 hours: 110 office, 226 off): office mean 36.2, σ 10.4, P99 53.1; off mean 3.0, σ 1.0, P99 5.3. With k = 2 the office threshold is 57.0 and one baseline hour exceeds it (0.5 false alarm per week); with k = 3 it is 67.5 and none exceeds it; k = 4 (77.9) gains nothing. At night mean + 3σ is only 5.9, so the floor of 25 applies. On the test Monday only 02:00 (486.0 MB) and 03:00 (512.4 MB) fire; the 10:00 payroll upload (62.2) and the 21:00 diagnostic upload (14.0) stay normal. Before calculating, remove periods with known incidents or planned exceptional work, check that every day of the week is covered, and record the baseline period; recalculate when the baseline is updated and review at least monthly (CIS Controls safeguard 13.11). Because Wazuh does not compute means, a small script writes one status line per hour (VDP-VOLUME host=PC-ACCT-01 hour=02 mb=486.0 profile=off-hours threshold=25.0 status=ABOVE) into a log file that Wazuh reads; a rule matching status=ABOVE raises AL-07. "The script calculates, Wazuh alerts."

3.5.3 Severity, notification and escalation

Severity measures how serious the possible consequence is; priority is the order of handling and combines severity with the importance of the asset and the time of day. The course scale: Critical (evidence of an attack in progress or of an attempt to hide activity on a priority asset; Wazuh levels 13–16; e-mail and text message at once), High (behaviour that often precedes an attack, or loss of visibility; levels 10–12; e-mail within 5 minutes), Medium (unusual behaviour with frequent legitimate causes; levels 7–9; daily digest at 08:00), Low (context and trends; levels 3–6; dashboard only). Read numbers in the right direction: Wazuh counts up (0 to 16, higher is more serious; alerts stored from level 3 by default); syslog counts down (RFC 5424: 0 Emergency to 7 Debug, lower is more serious).

A notification channel is the way an alert reaches a person: dashboard, e-mail, text message (SMS, Short Message Service) or phone call, help-desk ticket; faster channels interrupt people and are kept for the most serious levels. Three Wazuh defaults matter (alert management): only alerts of level 12 or more are e-mailed (email_alert_level), at most 12 e-mails per hour (email_maxperhour, the rest grouped), and Wazuh needs a local mail relay because it cannot authenticate to a mail server. Since High alerts are levels 10–12, AL-01 (level 10) would not be e-mailed by default: lower email_alert_level to 10 or add alert_by_email to the High rules. In the lab, e-mails go to a local mailbox only.

Each level needs a recipient named by role (so that the rule survives holidays), an acknowledgement target (the maximum time before someone confirms "I am handling this") and an escalation path (the next role when nobody acknowledges). At Val-des-Pins the owner is called when a Critical alert is not acknowledged within 15 minutes (the unacknowledged AL-05 of 07:58:40 reached the owner at 08:13:40); High alerts arriving at night are read at 07:00, an accepted risk decided in writing by the owner — the written decision is what distinguishes an accepted risk from an oversight.

Alert fatigue is the decline in attention and response quality when people receive more alerts than they can examine; it is measurable (unread alerts, growing acknowledgement times, ignored rules). Four controls: deduplication (one notification for repeats of the same rule and host within a window, with a count), grouping or aggregation (one message for related alerts, such as the daily digest), rate limiting or throttling (email_maxperhour) and documented suppression (not notifying a known, approved activity, with a reason and an end date). Workload check: with 60 minutes per day and about 8 minutes per High alert, fewer than 8 High alerts fit in a day; when normal days keep exceeding the budget, the rules must be tuned, not ignored. On the test Monday the matrix produced 12 notifications instead of 15 and a review workload of 92 minutes (116 without deduplication). Alerts inform; people decide the actions. Automated blocking (Wazuh active response) is not used in the course; any containment on a real system needs the owner's written approval, a change window and a tested rollback (Legal Notice section 7.4).

3.5.4 Testing, tuning and documenting alerts

A rule that has never fired may be correct or broken; only a test tells which. Alert testing is the controlled production of a safe event that should trigger the rule (positive test) or should not (negative test), followed by the comparison of expected and actual results; negative tests prove that the rule is not too broad. Four outcomes: true positive (TP, alert expected and raised), false positive (FP, no alert expected but one raised — wastes review time and feeds alert fatigue), false negative (FN, alert expected but none raised — the most dangerous outcome, because the team believes it is protected), true negative (TN). Precision = TP ÷ (TP + FP), the share of raised alerts that were justified; recall (detection rate) = TP ÷ (TP + FN), the share of expected detections that were made. The share of correct results among all tests (for example 9 ÷ 11 = 81.8 %) is accuracy, not precision.

Three safe ways to produce test events: the tool's test utility — wazuh-logtest on the manager or the dashboard page Ruleset Test (documentation) shows which decoder and rule match a pasted log line without creating a real event (saving the rule file is enough for wazuh-logtest; the manager must be restarted before the rule produces real alerts); a harmless real action on a lab machine with a test account (five wrong passwords); a synthetic log line written into a test file that the lab agent reads. Never test on a production system, on a shared network or with the account of a real person.

Tuning is the controlled change of a rule to remove false positives or false negatives (narrow a broad match, add a forgotten value such as logon type 10, adjust a threshold with baseline evidence, add a documented exception); after every change, regression testing runs the whole plan again, positive and negative, to prove the correction broke nothing. In the pilot, AL-05 v1.0 matched any line containing "cleared" (an application message about a browser cache raised a Critical alert — test T06, a false positive) and AL-03 v1.0 looked only at logon type 2 (a remote desktop logon at 22:15, type 10, was missed — T08, a false negative): version 1.0 scored precision 83.3 % and recall 83.3 % on eleven tests; version 1.1 scored 100 % on the same plan, which does not mean perfect detection in real use.

The alert register holds one entry per rule: identifier and version, purpose, data source, condition, rule type, severity, notification, response note, tests and outcomes, change history, owner and approval, next review (one month after approval and at every baseline update). A rule change is a configuration change: reason, test, approval and a way back (rollback). Keep each version of local_rules.xml; Wazuh leaves custom files in /var/ossec/etc/rules unchanged at upgrade but replaces the default rule files in /var/ossec/ruleset/rules, so never edit those.

Lesson 4.1 — Event logs: Windows and Linux

4.1.1 What an event log is, and the six questions

An event is one recorded occurrence (a logon, a service that starts, a packet the firewall refused). A log entry (also event record) is its written record, made of fields; an event log is the ordered collection of entries. Whatever the source, a complete entry answers six questions: when (time stamp), where (which system), from which source (which program or channel wrote it), what happened, who was concerned and from where (which address or workstation), together with the result (success or failure, and why). The fields that answer the questions differ from one source to another; the questions do not.

Two facts follow from the definition and justify everything else in the lesson. First, a log contains only what the system was configured to record: an event that the audit policy does not cover never existed in the log, which is why completeness is decided before an incident, not after. Second, a log is written by the system it describes, so whoever administers that system can modify or clear the local copy; the copy that has already left the machine is the one that counts.

4.1.2 Time: the field that makes two logs comparable

Entries from two systems can be ordered only if their clocks agree. NTP (Network Time Protocol, RFC 5905) corrects every clock at regular intervals; a difference of a few minutes between a firewall and a server (four minutes were found at Val-des-Pins) is enough to place an effect before its cause. Windows stores event time in UTC (Coordinated Universal Time) and displays local time; a traditional Linux syslog line carries the local time of the machine, without year and without time zone; a packet capture file stores UTC. Montréal in October is EDT (Eastern Daylight Time, UTC minus four hours), so 13:30 UTC and 09:30 EDT are the same moment. Rule: write the time zone once at the top of a timeline and convert everything to it; the international format is ISO 8601 (2026-10-08T17:42:10-04:00; a final Z means UTC).

4.1.3 The logging pipeline, the Windows channels and the Linux files

Every event goes through five stages: generation, local storage, collection (forwarding to a central server), central analysis, and alerting or reporting. The technician's work in Topic 4 happens in stages 2 to 4; Topic 5 triages the alert of stage 5.

On Windows, the Event Log service stores events in binary .evtx files under C:\Windows\System32\winevt\Logs, one file per channel. The three channels on every computer are Application (programs), System (the operating system and its services) and Security (the audit function: the results of the audit policy). Specialised channels appear under "Applications and Services Logs" (for example the Windows Defender operational log, the Task Scheduler log and, when Sysmon (System Monitor, a free Microsoft Sysinternals tool) is installed, a channel that records process creation with the command line and the network connections made by each process). Each event has a System part (provider, EventID, level, time of creation, EventRecordID — which increases by one per event, so a jump reveals a gap — and computer name) and an EventData part with named fields; the XML (Extensible Markup Language) field names are the names used by filters, scripts and Wazuh rules. The tools to read and export: the Event Viewer (eventvwr.msc, "Filter Current Log"), wevtutil (wevtutil gl Security shows size and retention; wevtutil qe queries; wevtutil epl exports a channel) and PowerShell Get-WinEvent with a filter hashtable, piped to Export-Csv to hand the events to a script. A standard channel is limited in size (about 20 MB by default) and overwrites its oldest events when full; the audit policy is read with auditpol /get /category:*. Forwarding solves both problems: WEF (Windows Event Forwarding) to a WEC (Windows Event Collector), or an agent (the Wazuh agent reads the channels through the Windows event log interface and sends them to the manager on port 1514/TCP (Transmission Control Protocol)).

On Linux, two logging systems usually run together: the syslog family (today almost always rsyslog, sometimes syslog-ng) writes plain-text lines under /var/log/, and systemd-journald keeps the same messages in a binary, indexed journal read with journalctl. The pairs to memorize: general messages in /var/log/syslog (Debian and Ubuntu) or /var/log/messages (the RHEL (Red Hat Enterprise Linux) family); authentication (SSH (Secure Shell), sudo, PAM (Pluggable Authentication Modules) sessions) in /var/log/auth.log or /var/log/secure — the Linux counterpart of the Windows Security log; kernel messages in kern.log and dmesg; package installations in /var/log/dpkg.log and /var/log/apt/history.log (the update log of Lab 2); the Linux Audit framework (auditd) in /var/log/audit/audit.log; and three binary files read with their own commands: wtmp with last, btmp with lastb, lastlog with lastlog. A classic syslog line has four parts: time stamp, host name, program name with its process number in square brackets, and the free-text message, whose vocabulary belongs to each program. The everyday commands are tail -f (follow a growing file), grep (filter), awk (extract fields), sort and uniq -c (count repeats), journalctl -u ssh --since "1 hour ago", journalctl -p err -b, and logger -p auth.warning "monitoring test", which writes a test message you then look for in the central tool — the standard way to verify that forwarding works end to end. logrotate renames auth.log to auth.log.1, compresses older copies and deletes copies beyond the retention count, so local retention is short; central retention is the one that counts. Files under /var/log belong to user syslog and group adm: only members of adm or sudo can read them, because they contain personal information.

4.1.4 The syslog message: facility, severity and PRI

The syslog format is standardized by RFC 5424 (the current standard) and RFC 3164 (the older BSD format still written by many systems). A message carries a facility (which subsystem produced it: kern 0, user 1, mail 2, daemon 3, auth 4, syslog 5, cron 9, authpriv 10, local0 to local7 = 16 to 23 — the local facilities are what firewalls and switches use) and a severity from 0 (emergency) to 7 (debug), where a lower number is more serious. The two are combined into the PRI (Priority value) written between angle brackets at the start of a message on the network: PRI = facility × 8 + severity. An informational (6) message from facility auth (4) has PRI 4 × 8 + 6 = 38, which is why such a line starts with <38>. The rsyslog rule auth,authpriv.* /var/log/auth.log uses exactly these two values. Forwarding is one rsyslog line: *.* @@logsrv.example.net:514 — one @ sends over UDP (User Datagram Protocol, fast, no delivery guarantee), two @@ send over TCP (reliable, and the base for TLS (Transport Layer Security) encryption, RFC 5425, port 6514).

4.1.5 Central collection, the common schema and the seven checks

Central collection means copying every entry, as soon as it is written, to a system that the monitored hosts cannot modify. It serves three purposes: the copy survives the clearing, filling or failure of the local log; all hosts become searchable together, in one place and one format; and retention is decided by the monitoring plan, not by the local file size. Val-des-Pins keeps 90 days (constraint C-03), the minimum of CIS Controls safeguard 8.10 and the practice described in NIST SP 800-92; the Canadian Centre for Cyber Security gives the same guidance.

A common schema is one fixed list of fields with one meaning each (time, host, source, event, outcome, account, source address, detail), filled from whatever the source provides; the translation is normalization, done by decoders in the monitoring tool or by a few lines of script. Once the entries share a schema, diagnosis becomes table work: sort by time, group by account, count by source address.

An entry is evidence only if the log it comes from can be trusted. The seven checks before trusting a log are: (1) clock — is the source synchronized by NTP and is its time zone known (timedatectl on Linux, w32tm /query /status on Windows)? (2) coverage — does the audit policy record what the monitoring need requires? (3) completeness — are there gaps (a cleared log, a full log that overwrote old events, a silent source)? (4) integrity — can the log be modified by the people it describes (a local administrator can clear a local log; the central copy cannot be cleared from the host)? (5) retention — how long are events kept locally and centrally? (6) access — who can read the log (the adm group on Linux, the Event Log Readers group on Windows, named dashboard accounts)? (7) format — is the format known and stable (version of rsyslog, of Windows, of the agent), so that a parsing script does not silently read the wrong field? The Lab 3 report has a section for them.

Logs are personal information. An entry names a person's account, the time of their work and their computer's address. Under Québec's Act respecting the protection of personal information in the private sector, as amended by Law 25, and federally under PIPEDA (Personal Information Protection and Electronic Documents Act), such records are collected at the minimum, protected, given only to those who need them and deleted when no longer needed. Course rule (Legal Notice section 7.2): every log file, baseline and alert record of the lab is personal information, stays in the lab and is deleted when the exercise is marked.

Topic 4

Lesson 4.2 — Network traffic capture: the basics

4.2.1 Frames, packets, headers and conversations

A log is written by the system that acts; a capture is a copy of what travelled on the wire, made by an observer that the acting system does not control. The two are complementary: the logs say which account did what on which host; the capture says what left the host, to which destination, how much and when. Hosts do not send files; they send small units. The transport layer splits the data into TCP segments or UDP datagrams and adds a header with a source and a destination port; the network layer wraps each segment in an IP (Internet Protocol) packet whose header carries the source and destination addresses, a protocol number (6 for TCP, 17 for UDP, 1 for ICMP (Internet Control Message Protocol)) and a TTL (Time To Live); the link layer wraps the packet in an Ethernet frame with the MAC (Media Access Control) addresses of sender and receiver. This nesting is encapsulation; the data carried by a layer is its payload. One frame of the night upload at Val-des-Pins was 14 bytes of Ethernet + 20 bytes of IPv4 + 20 bytes of TCP + a TLS record of 1,460 bytes; the largest Ethernet frame seen by a tool is 1,514 bytes without the check sequence; a UDP header is 8 bytes.

For monitoring, a handful of header fields answer most questions: the two addresses (who talks to whom), the protocol number, the destination port (which service), the TCP flags (SYN synchronize, ACK acknowledgement, FIN finish, RST reset — the state of the connection), the frame length and the time stamp. Addresses, ports and protocol form the 5-tuple that identifies one conversation (also called a flow); every statistic a tool shows ("top talkers", "conversations", "bytes per host") is computed by grouping packets on some part of it. A TCP connection opens with the three-way handshake: SYN from the client, SYN-ACK from the server, ACK from the client; FIN closes it and RST aborts it. The handshake exposes intent and result in three small packets: SYN answered by SYN-ACK means the port is open and a session started; SYN answered by RST means the port is closed; SYN with no answer means nothing listens or a firewall dropped it. Two application protocols are read because their headers carry names: DNS (Domain Name System, over UDP 53: the question name, the answer addresses and a TTL that says how long the client may keep the answer) and TLS, whose first message, the ClientHello, carries the SNI (Server Name Indication) in clear text before encryption begins. In encrypted traffic, what stays visible is who, with whom, which service, which name, how much, when and how the connection opened and closed; what stays hidden is the content and the account — those come from the host logs.

4.2.2 Where and how to capture

A capture tool reads the frames that reach one interface, and a switch forwards a unicast frame only to the port of its destination MAC address, so a workstation in promiscuous mode still sees only its own traffic plus broadcasts. To observe other hosts you must bring their traffic to your interface. The capture points: (1) on the host under study — quickest and complete for that host, but it modifies the machine you examine and the person using it can see, stop or alter the capture; (2) a mirror port (SPAN, Switched Port Analyzer) — the managed switch copies the frames of chosen ports or VLANs to the monitoring port without touching the production link, the usual choice in a small office, with one limit: a saturated mirror port drops frames (an unmanaged switch cannot mirror); (3) a hardware TAP (Test Access Point) inserted in a link — every bit at full speed, cannot be disabled by software, but needs a short interruption to install; (4) the firewall's own capture page, which sees what crosses the gateway and nothing that stays inside one switch. The lab stand-in for a mirror port is the VirtualBox host-only adapter of the monitoring VM set to Promiscuous Mode: Allow All. Capture as close as possible to the host you investigate, and avoid installing tools on a busy production server.

Storage decides the strategy. A 100 Mbit/s link fully used produces about 12.5 MB per second, roughly 45 GB per hour; Val-des-Pins rejected full capture of its Internet link (30 Mbit/s = 324 GB per day, about 29,000 GB over 90 days, 24 times the capacity of NAS-01) and accepted flow records exported by FW-01 (one record per connection with addresses, ports, bytes and duration: 37 GB over 90 days). Small networks therefore keep flow records (NetFlow, IPFIX, sFlow) or network metadata written by a sensor (Zeek writes conn.log, dns.log and ssl.log; Suricata writes eve.json), and run a full capture on demand, limited by a filter and bounded in time or size. A capture at a small company is a targeted source: started for one host and one question, for a bounded time, then stopped. The arithmetic to remember: bytes per second × 86,400 seconds × retention days.

All capture tools rest on libpcap (on Windows, Npcap). tcpdump is the command-line tool of Linux servers; Wireshark is the graphical analyser, with dumpcap as its capture engine and tshark as its text twin (tshark -r file.pcap -q -z conv,tcp prints the conversations table; -T fields exports chosen fields to CSV (comma-separated values)); Windows 10 and 11 include Pktmon (Packet Monitor), whose .etl output is converted with pktmon etl2pcap. The pcap file format has a 24-byte global header (magic number, version, snapshot length, link type) followed by one record per frame (time stamp in UTC, bytes kept, bytes on the wire); Wireshark saves by default in pcapng, and editcap -F pcap converts back. Four tcpdump options shape a capture: a capture filter (host 10.20.1.101 and not port 514); the snapshot length -s 256, which keeps every header and the TLS server name while dropping most content (a smaller file and less personal information; byte counts are then read from each record's original length); -n, no name resolution, so that the capture host does not itself send DNS queries while observing; and -G 3600 -W 8 (one file per hour, stop after eight files) so that a capture started at night cannot fill the disk by Monday (-C with -W rotates by size instead; -Z user drops privileges after opening the interface).

4.2.3 Capture filters versus display filters

Two kinds of filters exist and students confuse them constantly. A capture filter is written in BPF (Berkeley Packet Filter) syntax (host 192.168.10.44, net 192.168.20.0/24, port 53, tcp port 443, not port 22, src host 192.168.10.44 and not port 443), is applied by the capture library before frames are stored, reduces the volume, and cannot be undone: what it excluded was never recorded. A display filter uses Wireshark's own syntax (ip.addr == 192.168.10.44, tcp.port == 445, dns, http.request, tcp.flags.syn == 1 && tcp.flags.ack == 0, tcp.flags.reset == 1, tls.handshake.extensions_server_name), is applied to frames already captured, and can be changed as often as you like. The two are documented in the pcap-filter manual and the Wireshark wiki.

4.2.4 The capture record and the legal frame

"A capture that cannot be explained is not evidence." The capture record lists: the authorization reference; the operator and the start time (UTC and local); the capture point and the interface; the filter and the snapshot length; the tool and its version; the file names, sizes and SHA-256 hashes (proof that the file analysed is the file captured); the stop time and reason; the storage location and the deletion date. Capturing is interception: section 184 of the Criminal Code makes it an offence to knowingly intercept a private communication, and capturing other people's traffic on a network you share with them is interception whatever the intention; capturing on an employer's network without a written mandate is unauthorized use under section 342.1. Legal Notice section 7.2: capture only on interfaces of systems you own or that are Designated Targets, only for the duration of the exercise, never in promiscuous mode on a shared network (home, residence, campus, workplace), and treat every capture file as personal information. A guest Wi-Fi is excluded from every capture and every log (constraint C-05 at Val-des-Pins).

4.2.5 Reading a capture: five questions, in this order

Reading frames one by one is the last step, not the first. (1) Who talks with whom? — the conversations table (Wireshark: Statistics → Conversations and Endpoints). (2) How much? — bytes in each direction and the top talkers; a workstation that sends more than it receives is unusual, because a workstation normally downloads. (3) When? — the time column and bytes per second (Statistics → I/O Graphs). (4) Which service? — the destination port, the DNS name asked just before, the ClientHello server name; Statistics → Protocol Hierarchy shows the share of bytes per protocol, and a clear-text protocol such as Telnet or FTP (File Transfer Protocol) in 2026 is itself a finding. (5) How did it start and end? — a complete three-way handshake means the connection was opened normally by a program on the client; FIN closes, RST aborts, a SYN with no answer is a failed attempt. One source reaching many ports of one host in a short time, or many hosts on one port, is a pattern to send to diagnosis; so is a workstation contacting the same outside address at regular intervals, or a host sending far more out than in. What a capture cannot answer is which program on the host sent the traffic: that is in the host log (Windows event 4688 with its command line, or the Sysmon network connection event), which is why Lab 3 asks for both. A flow record answers who, with whom, how much and when; not the names and not the handshake.

Topic 5

Lesson 5.1 — What an anomaly (unusual activity) is

5.1.1 Four words that must stay separate

An event is a single observable occurrence (a logon, a connection, a file write); it has no opinion attached to it. A log record is the written trace of an event with its fields; one event can produce several records (the firewall and the server both see the same connection) and some events produce none, because nobody logs what nobody collects. A baseline is the statistical description of normal activity, always attached to a scope (which host, which metric) and a context (which hour, which day): normal at 10:00 on a Tuesday is not normal at 03:00 on a Sunday. An anomaly is an observation that deviates from the baseline beyond a tolerance. Every anomaly definition therefore has three parts: a reference (the baseline), a measure of deviation and a threshold; remove any of the three and the word has no meaning. The course outline calls an anomaly an "unusual activity": the word says nothing about intent.

5.1.2 Unusual is not malicious

A security incident is an anomaly caused by an actual or imminent violation of the organization's security policy — the confidentiality, integrity or availability of information (the CIA triad). An attack is a deliberate attempt by a person or a program to cause such a violation; an incident can also come from error or failure without any attacker. A false alarm is an anomaly that, once examined, has a harmless explanation. A precursor is a sign that an incident may occur in the future; an indicator is a sign that an incident may have occurred or may be occurring now; indicators specific enough to be shared and searched for (a file hash, a domain name, an address) are IoCs (Indicators of Compromise). The relation is inclusion, not equality: incidents ⊂ anomalies. Every incident starts as an anomaly; most anomalies are not incidents — on a network of fourteen people, a week of monitoring produces dozens of deviations, the large majority explained by maintenance, updates, backups, new software, holidays and human mistakes. That is why Lesson 5.2 exists.

5.1.3 Three families of anomalies

Family Definition Test Example
Point One observation is far outside the band of normal values, whatever the context Distance test: how far is this value from the mean? 112 connections in one hour when the baseline is 63 ± 15
Contextual An ordinary value at an abnormal time or place Conditional test: is this value normal given the hour, the day, the account, the host? 47 connections at 19:00 on a Thursday (baseline 3 ± 1.5) from a workstation that is normally idle after 17:00
Collective Each observation alone is ordinary; the set or the sequence is not Pattern test over a window: how many, how fast, in what order? 23 failed logons on 7 account names in 4 minutes; 16 ports of one host probed in 42 seconds

One episode can belong to several families; in a report, name the family that your detection rule actually tested, because that is what you can prove. The Class 14 scripts were collective detectors (counts in a window); Example 5.1 was a point and contextual detector (a z-score per hour of the day). Anomalies show up in three data sources — event logs, network traffic, and network files and system activity — and the same cause often appears in two of them; corroboration (the same anomaly from two independent sources) raises confidence, which the triage score rewards.

5.1.4 How a detector decides

A detector is the rule, program or tool component that turns records into a decision ("unusual" or "normal"). NIST SP 800-94 distinguishes three methods; practice adds two more:

  1. Signature-based — compares each record with a list of known bad patterns; precise for known threats and blind to new ones; strictly not anomaly detection, but the first thing a tool does.
  2. Threshold-based — counts records satisfying a condition inside a time window and compares with a fixed number chosen by a person from the baseline and the policy; simple, transparent, easy to tune.
  3. Statistical — computes from the baseline the mean and the standard deviation σ, then measures how many standard deviations the observation is from the mean: the z-score, z = (observed − mean) ÷ σ. A common tolerance is |z| ≥ 3; for a roughly bell-shaped metric, fewer than 0.3 % of normal observations fall that far from the mean.
  4. Behavioural (profile-based) — the baseline is kept per entity (user, host, service) and per context (hour, weekday); commercial products call this UEBA (User and Entity Behavior Analytics).
  5. Machine-learning — a model learns the shape of normal from many variables at once; it can find combinations no human would write a rule for, at the price of being harder to explain; not used in this course.

Two practical rules. A statistical test needs a long, clean baseline: a mean and σ computed from three days, or from a period that contained an incident, give a band that is either too narrow (constant false alarms) or too wide (misses). And add a minimum absolute difference, because a tiny baseline makes small changes look extreme: with a mean of 2 and σ of 1.2, an observation of 6 has z = 3.3 and would be flagged, although four extra connections at night mean nothing. Example 5.1 flags an hour only when |z| ≥ 3 AND |observed − mean| ≥ 10. Worked cases: Thursday 19:00, baseline 3 ± 1.5, observed 47 → z = 29.3, flagged; Friday 10:00, baseline 66 ± 15, observed 98 → z = 2.13, inside tolerance; Tuesday 03:00, baseline 2 ± 1.2, observed 6 → z = 3.3 but difference 4 < 10, the guard applies. A floor of 0.5 on σ protects the division against a standard deviation of zero.

5.1.5 The four outcomes and the base-rate effect

A true positive is flagged and unwanted; a false positive is flagged and harmless (a benign true positive when the rule worked correctly on authorized activity, such as the Patch-Wednesday update push); a false negative is unwanted and not flagged, found only by another detector or later; a true negative is the silent majority of records. The base-rate effect: 10,000 records a day with a 1 % false-positive rate give about 100 false alarms a day, far more than the handful of real incidents, so even a very good rule needs triage behind it. Lowering a threshold gives more true positives and more false positives; raising it gives the reverse: choosing the threshold is a decision about which error the organization prefers (Topic 6.4 revisits it).

5.1.6 Benign causes; security versus performance

Benign causes to document in the maintenance calendar and the allow-list before the alert arrives: scheduled jobs (backups, update pushes, definition downloads, month-end reports); changes (new software, new employee, new printer, a firewall rule added by the contractor); the calendar (holidays; the daylight-saving change on November 1 shifts every hourly baseline by one hour); failures (full disk, expired certificate, service restart loop); and people (late work before a deadline, a typing error repeated three times). A performance anomaly (slow server, saturated link, full disk) and a security anomaly (unauthorized access, data leaving the network) look alike at detection and differ at diagnosis; both must reach a human. The monitoring server's own log disk at 86 % (alert A-01) is a performance anomaly with a security consequence: if the disk fills, the server stops recording and every later detection becomes a false negative.

Topic 5

Lesson 5.2 — Reviewing and sorting alerts (triage)

5.2.1 From anomaly to alert

An alert is a claim, not a fact: "rule X matched record Y at time Z". It carries the rule, the time, the data source, the asset, the account, the addresses, a severity chosen by whoever wrote the rule, and a copy of or a pointer to the records. The detector has no knowledge of the maintenance calendar, of the fact that a designer works from home on Saturdays, or of the vendor contract that explains a large download. Verification happens in two stages: triage, which is short and decides whether and how fast the alert deserves attention (this lesson), and analysis, which is long and establishes what happened (Lesson 5.3). Triage routes; it does not investigate. Time box: 5 to 15 minutes per alert, so that the queue keeps moving. A feedback path returns benign and false alerts to the rules and the baseline (Topic 6).

5.2.2 Triage: the definition and the three verbs

The word comes from emergency medicine. The FIRST CSIRT Services Framework defines incident triage as the function that categorises, prioritises and produces an initial assessment of a reported event; NIST SP 800-61 Rev. 3 places it inside "detection and analysis" and calls prioritisation the critical decision, because the team cannot work on everything at once. The three verbs: categorise (what kind of alert — authentication, reconnaissance, outbound contact, data transfer, health of the monitoring itself — and what kind of outcome), prioritise (impact × confidence → position in the queue) and decide and record (escalate, investigate, monitor or close, with the reason, in a form that another person can read on Monday). In a large organization a level-1 analyst passes serious cases to level 2; at Atelier Nordik the technician is level 1, the IT (information technology) contractor is level 2 and the owner is the person called when an incident record is opened. The method is identical; only the names change.

5.2.3 The five triage questions

  1. What fired? — rule, data source, window, threshold. A count rule, an informational rule and an absence rule ("no logs for 60 minutes") are not read the same way.
  2. Where? — asset, zone, criticality (from the inventory), owner. The same rule on the domain controller and on a designer's workstation does not have the same impact.
  3. Who? — account and role. A privileged account raises the impact; a service account that never logs on interactively is itself a context.
  4. When? — time, duration, still going on, inside a maintenance window? An attack in progress ranks above an identical pattern that stopped yesterday. Read in one time zone, which is why clock drift is never irrelevant.
  5. How sure are we? — how many records, how many independent sources, allow-list, corroboration by another alert on the same asset, possible rule error.

5.2.4 Categorising the outcome

Five outcome categories, each with its handling: true positive — unwanted (stays open, prioritised); benign true positive — expected (the rule fired correctly on authorized, documented activity; closed with the reference to the document that explains it; if it returns every week, a tuning request); false positive — rule error (a mis-parsed record, a wrong threshold, a clock problem; closed, rule sent for correction); duplicate (merged into the existing alert, which gains a count and a "recurring" mark — recurrence raises confidence, it does not lower it); undetermined — needs information (kept open with a watch action and a date, never silently closed). Writing the right category in the ticket is what makes Topic 6 possible.

5.2.5 Severity is not priority

Severity is attached to the rule by its author, before any context. Priority is the order of work, computed in triage for this alert on this asset. Two scales from 1 to 5:

  • Impact (how bad if true; NIST SP 800-61 components: functional impact, information impact, recoverability). Practical scale: impact = max(rule severity, asset criticality), +1 for a privileged account, capped at 5. A domain controller at criticality 5 with the administrator account is impact 5 whatever the rule; a workstation at criticality 2 with a severity-3 rule is impact 3.
  • Confidence (how likely the alert describes real unwanted activity): start at 3 (plausible, unverified); +1 when an address or account in the alert is neither local nor in the allow-list; +1 when another open alert concerns the same asset (corroboration); −1 for an informational rule; forced to 1 when the maintenance calendar or the allow-list explains the alert.

Priority = impact × confidence, a score from 1 to 25, read in four bands: P1 Critical, 16–25 (acknowledge within 15 minutes, open the incident record, call the owner and the contractor); P2 High, 10–15 (investigate today); P3 Medium, 5–9 (investigate this week, Monday review); P4 Low, 1–4 (monitor, close if nothing new in 7 days). Two hand adjustments after the score: an activity that is still going on moves up one band; an alert about the health of the monitoring itself (a full log disk, a silent log source) is never ranked below P2, because while it lasts every other detection is a potential false negative. Why multiply rather than add: a certain alert about a trivial asset (1 × 5) and an uncertain alert about a critical asset (5 × 1) should both rank low; only an alert that is both serious and credible should reach the top — a product does that, a sum does not.

Worked example (Atelier Nordik, the weekend queue of twelve alerts): the repeated port-scan pattern from the workstation scored impact max(4, 2) = 4 and confidence 3 + 1 (unexplained destination) + 1 (two other open alerts on the same host) = 5, priority 20, P1; the burst of failures on the administrator account from an unknown VPN address scored impact max(4, 5) + 1 privileged = 5 and confidence 3 + 1 = 4, priority 20, P1; the web server that went silent scored max(3, 4) = 4 × (3 + 1) = 16, P1; the log disk at 86 % scored 4 × 3 = 12, P2 — and health alerts are never below P2 anyway. The nightly batch logon of the backup account inside its calendar window, the designer's three failures then success from her allow-listed VPN address, and the vendor-mirror download in its synchronisation window were closed as benign (confidence forced to 1). Equal scores are ordered oldest first; a position changed by hand needs a written reason.

5.2.6 Aggregation, correlation and known-good lists

Aggregation merges records of the same kind into one alert (23 failures = one alert with a count of 23, not 23 alerts; tools group by rule, asset and source within a window, sixty minutes being common). Correlation links different alerts that share an entity (host, account or address) and is the basis of the corroboration bonus: three alerts on one workstation can describe one story that no single alert tells. The allow-list holds addresses, accounts and behaviour patterns documented as legitimate, with the reason and the document that proves it; the maintenance calendar holds planned windows with the asset, the activity and the responsible person. Pitfall: a window must be matched on asset, time AND activity. The nightly backup window of the server (02:00 to 03:00) explains the batch logon of the backup account at 02:00; matched on asset and time only, it would also have excused fifteen failures on "administrator" at 02:40 from an unknown address. Attackers do not consult your calendar, but they do like quiet hours; a known-good rule that is too broad is a false negative waiting to happen.

5.2.7 Recording the decision

"A decision that is not written down does not exist." The minimal record (a ticket, a spreadsheet row, a note in the tool) holds: identifier; time (UTC and local); source; rule; asset; account; addresses; category; outcome; impact; confidence; priority; justification; decision; next step; a named responsible person; due date; status; pointers to the raw evidence (the log lines, file names, capture — raw and unmodified, never "cleaned"); time of review; reviewer. Monitoring data are confidential: Legal Notice sections 6.7, 7.2 and 17 and the privacy obligations summarised in its section 8.3 apply to every ticket.

5.2.8 Alert fatigue and the six common mistakes

Alert fatigue is the state of a person or a team that receives more alerts than it can read with attention; the predictable result is that alerts are closed without being examined, and the real incident is closed with them. The cure is upstream (fewer, better alerts — Topic 6) and downstream (the triage discipline). The six mistakes, in the order beginners make them: (1) ordering the queue by rule severity alone; (2) handling the newest first — the queue is ordered by priority, then by age, oldest first; (3) closing without a reason ("looks fine" is not a reason); (4) ignoring health alerts (a full disk or a silent source is a loss of visibility: while it lasts, the quiet queue proves nothing); (5) treating a quiet queue as a safe network — silence is also what a false negative looks like; the only remedy is coverage (Topic 6.3) and periodic review of the baseline; (6) over-broad known-good rules — every exception must name the activity it excuses.

Topic 5

Lesson 5.3 — Analyzing anomalies step by step

5.3.1 Key terms and the three errors the method prevents

Triage answered "which alert first?"; analysis answers three other questions: what exactly happened, in what order, and how sure are we. The answer must be reproducible: another technician with the same files and the same steps must reach the same conclusion. In the NIST Cybersecurity Framework 2.0 this is the category Incident Analysis (RS.AN). Evidence is any record that can support or contradict a statement about what happened (an event-log entry, a console export, the state of a configuration, a change ticket, a written statement of a person). A hypothesis is a possible explanation that makes predictions you can check: "if this explanation is true, we should find this record, and we should not find that one." Corroboration is the confirmation of a fact by a second source independent of the first. A finding is a statement that the analysis has established, written together with its evidence. Confidence (low, medium, high) says how strongly the evidence supports a finding.

The method prevents three errors. Confirmation bias: looking only for the evidence that supports the explanation you already prefer; prevented by writing every hypothesis before reading the evidence in detail and testing the benign ones first. Mixed time zones: a console writes UTC, workstations write local time with an offset, an alert queue writes local time without one; sorted without conversion, a cause appears after its effect; prevented by converting every time to one zone before sorting. Single source: one record from one system shows only what that system recorded (a console can display a wrong status, an account can be used by someone else); prevented by confirming each important fact with at least two independent sources.

Order of volatility. RFC 3227, Guidelines for Evidence Collection and Archiving (IETF, also BCP 55), asks you to collect the most volatile data first: (1) registers and cache; (2) routing table, ARP (Address Resolution Protocol) cache, process table, kernel statistics, memory; (3) temporary file systems; (4) disk; (5) remote logging and monitoring data relevant to the system; (6) physical configuration and network topology; (7) archival media. When an attack is still in progress, the network connections and the running processes come first, because they disappear when the program stops or the computer restarts; for a case whose facts are in event logs, console exports and a ticket, nothing volatile is needed.

Hypothesis results. Each test has one of four results: supported (the predictions are found), refuted (a record contradicts a prediction), not supported (the evidence found does not support it but cannot exclude it) or undetermined (the records needed could not be obtained). A refuted hypothesis is a result: write it down, because it tells the next person what has already been checked. Benign hypotheses are tested first because they are more frequent and cheap to check; the adversary hypothesis is always tested too, because an attacker can act during a maintenance window or make a malicious change at the same time as an approved one.

Independence. Two sources are independent when an error, a failure or a falsification in one cannot change the other: different systems, different collection paths, different administrators. A console's device status, update history and audit log form one group (one fault or one stolen console account affects all three). A person contacted out of band — by phone at the number written in the service contract, never a number found in an e-mail or in the console — is a separate source. Minimum: two independent groups for a finding; three or more for high confidence. Use exact words: "no evidence of X" is not "X did not happen"; the absence of a record proves nothing if the source could not have recorded the event (logging not enabled, retention too short, source not collected). Write what was checked.

5.3.3 The worked case: alert A-09 at Atelier Nordik

The daily device-health check of the antivirus console raised A-09 on Saturday at 09:30: three rendering workstations had had no successful definition update for more than 24 hours. Triage had scored it 2 × 3 = 6, P3. On Tuesday the technician collected eight files from five independence groups (the console, the workstations' own Defender event logs, the file server's share listing, the contractor's change log and the maintenance calendar), hashed each at collection, and built a 30-row timeline in EDT. Read in one time zone, the timeline showed the change (Thursday 17:42, policy Render-WS pointed to a file share on the server, no fallback) 3 hours 33 minutes before the first failed update (21:15, error 0x80070035, "The network path was not found"), then one failure every four hours on each workstation. Four hypotheses were written: H1 the workstations were off (refuted — the console saw them online and each tried every four hours); H2 the publisher's update service was down (refuted — the nine other workstations made 102 successful updates); H3 a documented change explains the failures (supported by four groups: ticket CH-2026-090 with step 2 done and step 1 — create the share — never done; the console audit; the workstation errors naming that exact path; the share absent on the server); H4 someone tampered with the antivirus (ATT&CK T1685, not supported — usual contractor account, usual address, multi-factor sign-in, approved ticket, real-time protection still on — and confirmed out of band by a phone call to the contract number). Preliminary conclusion: monitoring failure, confidence high, priority raised from P3 to P2, three open questions.

Topic 5

Lesson 5.4 — Diagnosing incidents and documenting the findings

5.4.1 Key terms and the three questions that decide the category

The analysis produced findings; the diagnosis turns them into a decision other people can act on: what kind of problem it is, why it happened, how far it reached, what it cost or could have cost, how urgent it is. A security incident, in the words used by NIST SP 800-61 Rev. 3 (taken from the United States Federal Information Security Modernization Act of 2014), is an occurrence that actually or imminently jeopardizes, without lawful authority, the integrity, confidentiality or availability of information or an information system, or constitutes a violation or imminent threat of violation of law, security policies, security procedures or acceptable use policies. A monitoring failure is a monitoring or protection tool that stops collecting data or stops protecting, without an attacker (logs not collected, agent stopped, disk full, updates failing): not an attack, but a period during which an attack would be neither detected nor blocked. A benign outcome is authorized, expected activity: the rule fired correctly (benign true positive) or the rule itself was wrong (false positive).

Three questions decide the category, asked in this order; the first "yes" decides: (1) Did someone act without authority, or was a security policy violated? → security incident. (2) Is a monitoring or protection tool failing? → monitoring failure. (3) Was the activity authorized and expected? → benign. A monitoring failure caused by an attacker is a security incident, because question 1 comes first. If the answer is "no" to all three, the analysis is not finished: collect more evidence and repeat the five steps. What follows each category: a security incident is contained, eradicated and recovered, its ATT&CK techniques are mapped and its evidence preserved, and the legal notification checks are always run; a monitoring failure is fixed, the fix is verified with evidence and the lessons are written; a benign outcome is closed with the reason, and the rule is tuned or given a scoped exception.

5.4.2 Root cause, scope, exposure window

The immediate cause is the condition that directly produced the symptom; the root cause is the most basic cause that, once removed, would have prevented the problem and will prevent it from coming back. Find it by asking "why?" until the answer is a decision or a process that people can change. For A-09: why did the updates fail? — the workstations looked for definitions in a share that does not exist; why does the policy point there? — step 2 of the change was applied; why does the share not exist? — step 1 was never done; why did nobody notice before Saturday? — the ticket had no verification step, the change was not in the maintenance calendar, and the health check runs once a day with a 24-hour threshold. Root cause: the change process allowed a change to be applied without a verification step and without a calendar entry. Contributing factors: step 2 done before step 1; the policy kept no second update source. A root cause is written as a fact about a process, not a judgment about a person: "step 1 was skipped and nothing checked it" leads to a better process; "the contractor is careless" names nothing a process change can fix. "The share does not exist" is the immediate cause, not the root cause: creating the share fixes this case, but the same process would let the next change fail the same way.

The scope is the set of assets, accounts and data affected. The exposure window is the period during which the weakness existed, measured from evidence: from the first moment of exposure to the verified end — for A-09, from the first failed update (Thursday 21:15) to the last workstation updated after the fix (Tuesday 10:46): 4 days 13 hours 31 minutes. The detection delay is the time between the start of the exposure and the alert: 36 hours 15 minutes. Measuring from the alert time would leave out 36 hours of exposure; measuring from the change (17:42) would add 3.5 hours during which the definitions were still current.

5.4.3 Impact, priority, adversary behaviour, confidence

Rate the impact on each property of the CIA triad with three levels: none, potential (possible but not observed), confirmed (observed in the evidence). A-09: confidentiality none, integrity potential (a new threat would not have been recognized), availability none. Priority after diagnosis uses the triage scale, impact × confidence, with the same bands (P1 ≥ 16 "now", P2 10–15 "today", P3 5–9 "this week", P4 ≤ 4): A-09 went from 2 × 3 = 6 (P3) to 2 × 5 = 10 (P2) because four independent groups raised the confidence to 5; the hand rule (monitoring or protection health never below P2) would already have given P2 at triage. The priority changed because the knowledge changed, not because the alert changed, and the record says so.

Assign a MITRE ATT&CK technique only when the evidence shows the behaviour, and also write the techniques you tested and refuted. Version matters: in ATT&CK version 19 (current since April 28, 2026) the former Defense Evasion tactic was split into TA0005 Stealth and the new TA0112 Defense Impairment, whose technique T1685 Disable or Modify Tools covers stopping security services, changing their configuration or blocking their updates; older documents cite T1562.001 for the same behaviour. Always write the version you used. Other techniques of the course: T1046 Network Service Discovery, T1110 Brute Force, T1078 Valid Accounts, T1053 Scheduled Task/Job, T1133 External Remote Services, T1571 Non-Standard Port.

Confidence levels: high — three or more independent groups agree, no record contradicts, the mechanism is explained ("the evidence shows that…"); medium — two groups agree, or one gap remains ("the evidence indicates that…", "probably"); low — one source only, or sources disagree ("one record suggests that…", "possibly"). A confidence level is a statement about the evidence, not about the analyst; it changes when new evidence arrives.

5.4.4 The diagnosis record and the chain of custody

One diagnosis record per case, written while you work, not from memory afterwards, in eleven sections: (1) what happened (facts only, two to four sentences); (2) category, with the answer to each decision question and the evidence identifiers; (3) root cause; (4) scope and exposure window; (5) impact (CIA) and priority before and after diagnosis; (6) adversary behaviour (techniques supported, or tested and refuted); (7) confidence with its reason; (8) key timeline with file and line, full timeline attached; (9) actions taken — a contemporaneous log (time, person, action, result, written at the moment); (10) evidence register (identifier, file, source, collector, time, SHA-256); (11) open questions and lessons. Rules: facts and interpretations are written separately; every fact has a reference (evidence identifier, file, line); uncertainty is stated with the confidence level and the open questions; the record is labelled (TLP:AMBER+STRICT for A-09) and stored with need-to-know access, because monitoring data are personal information.

A hash value is a fixed-length number computed from the bytes of a file; with SHA-256 (NIST FIPS 180-4) it has 256 bits written as 64 hexadecimal characters; the same bytes always give the same value, changing a single byte changes the value almost completely (one letter changed in a copy of the calendar file changed 60 of the 64 characters), and it is computationally infeasible to build a different file with the same value. The evidence register lists every file with its hash, size, source, collector, time and method; integrity verification recomputes the hash later and compares it with the register; the chain of custody records every person who held the evidence, when and why, from collection to the end of the case (RFC 3227; NIST SP 800-86). Practice: keep the originals read-only, work on copies, and never open an evidence file with a program that saves automatically — a spreadsheet that reformats dates and saves changes the bytes and the hash. A course exercise is not admissible forensic work: at work, follow the employer's incident response plan and chain of command (Legal Notice section 7.8).

Lesson 5.5 — Communicating results to the people concerned

5.5.1 Who needs to know, and the Traffic Light Protocol

A correct diagnosis that reaches the wrong person, too late, or in words the reader cannot use, changes nothing; effective communication with stakeholders is a performance criterion of EZ01 and a category of the NIST Cybersecurity Framework 2.0 Respond function (RS.CO). A stakeholder is a person or organization affected by the problem, who must act on it, or who must be informed by law. The need-to-know rule: a person receives a piece of information only if they need it to do their part; it protects the people whose data appear in the evidence and avoids alarming people who cannot act. List the stakeholders by role — the decision maker (the owner), the people who fix the problem (the contractor), the people affected (the users), the people who might be affected (other staff, clients) and the authorities (privacy regulators, the Cyber Centre, the police) — and decide yes or no for each, with the reason: a "no" is a decision too, and it must be possible to check it later. For A-09 there were three recipients and six deliberate non-recipients. The communication record lists who was informed, of what, when, by whom, through which channel and under which label, and who was deliberately not informed, with the reason.

The Traffic Light Protocol (TLP) version 2.0, published by FIRST (Forum of Incident Response and Security Teams) in August 2022, is a set of labels that tell the recipient how far they may share a piece of information: TLP:RED — the individual recipients only, no further disclosure; TLP:AMBER+STRICT — the recipient's own organization only; TLP:AMBER — the recipient's organization and its clients, on a need-to-know basis; TLP:GREEN — the community (peers and partners), not public channels; TLP:CLEAR — anyone, no limit except copyright. In a document the label is written in the header and the footer of every page; in an e-mail, in the subject line and directly before the labelled information. A-09: the owner note and the diagnosis record carried TLP:AMBER+STRICT, the technical annex for the contractor TLP:AMBER, the users' message TLP:GREEN. A TLP label is an instruction to people; it does not encrypt or technically protect the file.

5.5.2 When and how: "speak before you act, write after you verify"

Timing follows priority (P1 now, P2 today, P3 this week). A decision that changes a system (reverting a policy) is agreed by phone with the person who has the authority (the owner) and the person who will make the change (the contractor); the written messages are sent after the fix has been verified, so that they contain verified facts — writing before verifying produces messages that must be corrected later. Contact people out of band: the contractor is called at the number written in the service contract, not at a number found in an e-mail or in the console, because if the adversary hypothesis had been true an intruder holding the console account or a mailbox could have answered in the contractor's place. Every conversation is recorded in the actions log at the time it happens.

Lesson 6.1 — Updating the reference databases

6.1.1 What a reference database is, and why references age

A reference database is any stored description of what is known or normal, against which a detector compares an observation. A working setup relies on five families: (1) the baseline (statistics of normal activity per host, per hour, per account); (2) the asset inventory with its criticality scale (1 to 5), which tells triage how much an alert matters; (3) the known-good lists — the allow-list, the maintenance calendar and the list of service accounts; (4) the detection references — antivirus definitions, intrusion-detection rule sets (Suricata, Snort), reputation lists and threat-intelligence feeds (what is known to be bad everywhere, not only here); (5) the vulnerability references — the CVE (Common Vulnerabilities and Exposures) feed of the vulnerability scanner and the software version inventory. The first three are local (they describe this network) and are updated by recomputing; the last two are external (they come from a publisher) and are updated by fetching and verifying. The age of each reference is the KPI (Key Performance Indicator): definitions no older than 8 hours (two update cycles of four hours), the baseline no older than 35 days, the inventory updated the same day as any change, the calendar updated at the moment a change is approved.

References age for three reasons: drift (normal activity changes when a designer joins, a project moves working hours into the evening, or a software update doubles an application's connections — "the baseline of September does not describe October"); new threats (an unrefreshed detection reference cannot recognise a signature published after its last update; the Cyber Centre's guidance on updates, ITSAP.10.096, treats an outdated system as a vulnerability in itself); new assets (a device absent from the inventory has no criticality, is in no coverage matrix and receives no monitoring). Case A-09 was exactly an age problem: definitions aged for four days because the update path was broken by an unverified change, and the rule measured the age only once a day.

6.1.2 Updating a baseline without poisoning it — four rules

  1. Bounded window: the last four to six weeks of workdays. The baseline file keeps, per hour, the sample count n, the mean and the standard deviation — not the raw counts — because with these three numbers an old group and a new group of samples can be combined exactly: pooled mean = (n₁ × m₁ + k × m₂) ÷ (n₁ + k); pooled variance = [(n₁ − 1)·s₁² + (k − 1)·s₂² + n₁·(m₁ − m)² + k·(m₂ − m)²] ÷ (n₁ + k − 1). An old week is dropped by leaving it out of the pool, not by subtracting it.
  2. Exclusions: hours of a confirmed incident never enter the statistics. If the scan hours of Thursday October 8 had been included, the 19:00 mean would have moved from 3 to about 6 and its standard deviation from 1.5 to about 12; the next scan at 19:00 would have produced a z-score of 3.5 instead of 29, at the edge of the threshold after one contaminated week and below it after two. This is baseline poisoning (also contamination), the most common way a detector loses sensitivity without any rule being changed.
  3. A separate profile for approved-but-different activity: the Patch-Wednesday hours (first Wednesday of the month, 14:00 to 16:00, from the calendar) produce 112 connections where the workday mean is 63; mixing them in would widen the band for every Wednesday. A separate "patch-day" profile is used only once it has at least five samples (minimum sample count); until then the calendar provides the context.
  4. Version the file and write a change record: baseline_hourly_v2.csv next to v1, and for each hour the old statistics, the values added, the values excluded and the new statistics. A reference database is never edited in place.

In Example 6.1, the week of October 6 to 9 was sorted into 2 excluded hours (the incident), 2 maintenance hours (Patch Wednesday) and 92 ordinary hours; the three largest moves of the mean were 10:00 (66.0 → 69.1: (10 × 66 + 91 + 63 + 56 + 98) ÷ 14 = 69.14), 17:00 (30.0 → 32.6) and 11:00 (64.0 → 61.6), all small, as expected for a stable workstation. The back-test flagged the same three hours under v1 and v2; with calendar context the Patch-Wednesday flag became an INFO. Two limits to state: the back-test was in-sample (it replayed the week that fed v2; the real test is the following week), and the reduction of alerts came from the calendar, not from the new statistics.

6.1.3 Updating detection references with verification

Six steps: (1) source — the official publisher, over an authenticated channel, never a mirror found by a search engine; (2) verify the origin — compare the published hash or signature and the version number (Legal Notice section 14.2 and Annex C ask for a VirusTotal check of any downloaded file); (3) test — in the lab first, with a snapshot; for a baseline, a back-test over the last week; (4) deploy — inside a maintenance-calendar window, with a rollback; (5) verify the effect — the KPI moved as expected and the known incidents are still detected; (6) record — version, date, who, what changed, why. Two consequences: a failed update is a monitoring-health event, never triaged below P2 by the hand rule of Lesson 5.2, because a reference that stops updating removes protection silently; and an update of a reference database is a change in the sense of the change process — ticket, calendar window, verification step — the three things that were missing from the change that caused A-09. Frequencies by family: definitions every 4 hours automatically, rule sets daily, feeds hourly, the baseline monthly, the inventory and the calendar at every change. The maintenance calendar is a known-good list maintained by a process (whoever approves a change updates it at the moment of approval), not by a download.

Topic 6

Lesson 6.2 — Reducing the impact of monitoring on network performance

6.2.1 Four cost components and passive collection

Monitoring has a cost with four components: bandwidth (the mirrored copy of the traffic, log forwarding, flow export, management polling); host resources (processor time and memory used by agents, by a verbose audit policy or by a local capture); collector storage (every byte received is written, indexed and kept for the retention period); sensor capacity (a sensor that receives more frames than it can process drops some, and a dropped frame is an event that never existed for the detector). A fifth cost is not technical but real: every gigabyte stored must be searchable by an analyst during an investigation. A performance problem caused by monitoring is the fastest way to have the monitoring switched off.

Passive collection costs the production links nothing. A SPAN (Switched Port Analyzer) session, also called port mirroring, has the speed of one port, and the two directions of the mirrored link add up on it: an uplink at 600 Mbit/s each way produces a 1.2 Gbit/s copy, and above 1 Gbit/s the switch silently discards part of it; at Atelier Nordik the SNMP poller measures the LAN uplink at 38 Mbit/s average, 420 Mbit/s peak (both directions), which fits the 1 Gbit/s mirror port with a margin. A network TAP never drops and never loads the switch, but needs a second sensor interface and a short interruption of the link to install (450 CAD in the proposal). An inline sensor (an intrusion prevention system in the path) adds latency to every packet and becomes a point of failure (fail-open or fail-closed); in a 14-person firm with one operator, passive collection is the default and inline devices are reserved for the perimeter. The misconception to correct: "a SPAN port is free" — free for the production links, not for the mirror port and not for the sensor; the sensor's drop counter is the first KPI of this lesson.

6.2.2 Reducing the volume — three techniques and what each one loses

  • A capture filter (BPF, Berkeley Packet Filter syntax) discards known-good bulk conversations at the sensor before they are written: the SMB backup copies to the server and the HTTPS downloads from the vendor mirror were 88 % of the bytes of the Thursday sample and carried no detection value. Loss: those conversations become invisible; the coverage matrix must say so.
  • Flow records (NetFlow, the IPFIX standard, sFlow as a sampled variant) keep one record per 5-tuple with counters (bytes, packets, flags, start and end), at 1 to 8 % of the packet volume; an exporter on the firewall sees every conversation that crosses it (LAN to DMZ, LAN to WAN (Wide Area Network), VPN to LAN) but nothing that stays inside one segment. Loss: the payload — who talked to whom, when and how much, never what was said.
  • Sampling keeps one frame in N: the cheapest and the most dangerous reduction for security. At 1:10 the 16 frames of a port scan lasting under 20 seconds keep on average 1.6 frames, far below the 10-port rule, and six SYN frames sent 10 seconds apart survive with a probability of only about 47 % (1 − 0.9⁶); in the sample, none of the 22 frames survived. Sampling is acceptable for capacity planning, not for detection rules that count events.

Reducing the load at the source: keep every security event (Windows 4624, 4625, 4688, the antivirus events 2000 and 2001, the Linux authentication records) and drop debug or verbose application records before they leave the host (measure: events per second per source); poll utilisation counters every 5 minutes and let traps report urgent states (polling every 10 seconds generates thirty times the management traffic); schedule heavy jobs (weekly vulnerability scan, full capture, re-indexing) outside business hours and write them in the maintenance calendar, otherwise they become alerts (the Sunday 04:00 scan produced four false alarms in Example 6.4); buffer and compress on the forwarders; rotate and tier retention (90 days searchable, one year compressed) so that the collector's disk stays under its threshold (A-01 was the disk at 86 %).

6.2.3 Measure before and after; the one rule above cost

KPIs measured before and after any change: mirror-port utilisation (%), the sensor drop counter, gigabytes written per day, events per second per source, agent processor use on a workstation. The rule that ranks above every saving: never remove the data that a detection rule depends on. Each reduction is traced to the rules it affects: a capture filter that drops port 445 also drops the evidence of the next lateral movement over SMB inside the LAN, unless the authentication logs (and, for traffic crossing the firewall, the flow records) still cover it. This is why coverage (6.3) is decided before cost (6.2): the cheapest strategy that keeps every needed detection is the right one, not the cheapest strategy. Law 25 adds the data-minimisation argument: a budget that stores 410 GB of full packets per day "in case" is both a performance problem and a privacy problem.

Example 6.2 — the monitoring budget of the LAN mirror. Daily volume of a 38 Mbit/s link: 38 × 1,000,000 ÷ 8 × 86,400 ≈ 410 GB per day. On the 68-frame sample: strategy A, full capture, 27,665 bytes → 410 GB/day, 1.2 days of retention on a 500 GB budget; B, filtered capture (backup to the server and vendor HTTPS removed), 11.7 % → 47.8 GB/day, 10.5 days; C, flow records (46 flows × 48 bytes), 8 % → 32.75 GB/day, 15 days; D, 1:10 sampling, 1.7 % → 7 GB/day, 72 days, but no detections. Full, filtered and flow strategies all keep the two Example 4.2 detections (16 distinct ports, 6 SYNs to port 4444); sampling keeps neither. Decision: B for the LAN mirror (packet detail needed for signatures), C for the DMZ and VPN segments (not mirrored at all), D rejected for detection, A rejected for cost.

Topic 6

Lesson 6.3 — Improving monitoring coverage

6.3.1 What coverage is, and seven ways it is lost

Coverage is the share of what we need to observe that we actually observe, in three dimensions: assets (every device of the inventory, weighted by criticality), data sources (authentication logs, process creation logs, antivirus health, firewall decisions, VPN sessions, flow records, packet mirrors, web server logs, DNS queries, time synchronisation) and detection needs (the questions the rules and the analysts must be able to answer). The instrument is the coverage matrix — assets in rows, sources in columns, each cell collected, available but not collected, missing or not applicable. A required cell that is not collected is a gap; a gap that prevents a question from being answered is a blind spot. Coverage is not volume: the LAN mirror delivers 410 GB per day and the score is still 58.8 %, because the volume comes from one segment while the gaps are on the firewall, the VPN, the DMZ and the workstations' process logs; seven of the eight October needs were blocked.

The seven ways coverage is lost: (1) source not collected — the device produces the data but nobody forwards it (the firewall keeps its filter log locally for seven days); (2) event type not enabled — the audit policy does not record process creation and no Sysmon is installed, so no host can say which program opened a connection; (3) segment not observed — only the LAN uplink is mirrored, the DMZ side and the VPN pool are invisible to the sensor; (4) silent source — the web server stopped sending on Saturday and nobody was told, because no rule watches the sources themselves; (5) clock drift — a workstation 2.4 seconds off cannot be placed on one time line with the others; (6) retention too short — a question asked on Tuesday about Thursday evening needs the records to still exist; (7) encrypted or summarised traffic — the mirror sees HTTPS to the vendor but not its content; only flows, DNS and the TLS handshake metadata remain informative. The joint guidance Best practices for event logging and threat detection (led by the Australian Cyber Security Centre, co-signed by the Canadian Centre for Cyber Security and partners, August 2024) lists the same conditions from the organization's side: an approved logging policy, centralised collection and correlation, secure storage with integrity, and a detection strategy for the threats that matter.

6.3.2 Needs, techniques, the coverage method and the score

A detection need is a question with the sources that answer it; questions come from the open items of the investigations, from the rules we run and from the attack techniques we have decided to see. For the last group the course uses MITRE ATT&CK version 19, where each technique lists its data sources: brute force (T1110) needs authentication logs and a live source; the identity behind a VPN address (T1133 External Remote Services) needs the VPN session log; the program behind a scan (T1046 Network Service Discovery) needs process creation events; a connection on an unusual port (T1571 Non-Standard Port) needs the firewall decision; an attacker who stops the tools (T1685 Disable or Modify Tools, tactic TA0112 Defense Impairment) needs antivirus health and source-health events.

The coverage method has seven steps: list the needs; list the assets with criticality; record the status of each source per asset; build the matrix; compute the score; rank the gaps; close them, cheapest first on equal weight. Coverage score = Σ(criticality × collected cells) ÷ Σ(criticality × required cells), a partial source (available but not collected) counting one half; Atelier Nordik in October: 70 ÷ 119 = 58.8 %. A missing source on the domain controller (criticality 5) costs five times a missing source on a workstation. Gap weight for ranking = criticality × number of needs the gap blocks (at least 1); ties go to the cheapest closure. The required sources per asset type are themselves a reference database (servers: authentication log, process log, antivirus health, syslog forwarding, source health, NTP; the firewall: filter log, VPN log, flow export, syslog forwarding, NTP; workstations: authentication log, process log, antivirus health, NTP). The top three of the fourteen ranked gaps were the web server's source-health rule (weight 8 = criticality 4 × 2 needs, effort 1), the domain controller's source-health rule (5, effort 1) and the firewall's syslog target (5, effort 1): the answer to "which cell first?" is not the biggest gap but the best weight-to-effort ratio — the link to Lesson 6.5.

6.3.3 Monitoring the monitoring: source health

The largest single improvement of coverage is usually not a new source but a rule about the existing ones. A source-health rule (a heartbeat) alerts when a source that normally produces events has produced none for a defined interval — 30 minutes for servers and the firewall in the proposal — and the alert is P2 by the hand rule, because silence is indistinguishable from an attacker who disabled logging. It needs two reference inputs: the expected rate of each source (a small baseline) and the maintenance calendar (a planned reboot is not silence). It would have found the silent web server at 11:50 on Saturday instead of during triage on Sunday.

Topic 6

Lesson 6.4 — Improving the quality and accuracy of results (fewer false alarms)

6.4.1 Four outcomes, two ratios, five causes

Quality is measured with the four outcomes (true positive, false positive = false alarm, false negative = miss, true negative) and two ratios: precision = TP ÷ (TP + FP), the share of alerts that were correct — the ratio the analyst experiences directly; recall (also sensitivity or detection rate) = TP ÷ (TP + FN), the share of real events that were detected — what the organization discovers after an incident. Tuning means raising precision without lowering recall. A benign true positive belongs to the TP column: a correct alert about approved activity, closed with a reason code, the rule left alone. Over the four weeks September 14 to October 11, Atelier Nordik's rule set v1 produced 51 alerts: 7 true, 2 benign, 42 false, and 1 slow attack missed — precision 0.18, recall 0.86. An analyst who opens nearly 13 alerts a week with fewer than two about a real event stops reading them: alert fatigue is the mechanism by which a true alert is closed without being read.

Five causes of false alarms ("the cause chooses the remedy"): (1) a stale reference — a service account whose password had been changed by mistake generated 12 failed logons every night for four weeks, 28 of the 42 false alarms from one cause; the remedy is to fix the password (a process), not the rule; (2) a rule without context — the baseline rule fired on Patch Wednesday because it did not consult the calendar; (3) a measure that does not represent the failure — the definition-age rule fired on laptops that were switched off and waited 36 hours on the real failure: the age of the last success is not the same thing as a failed attempt; (4) approved activity that looks like an attack — the authorized weekly scan from the monitoring server and the vendor's contracted support session; (5) a threshold on the wrong time scale — 10 failures in 10 minutes caught two fast attacks and missed a slow one at 8 failures per 10 minutes for an hour: a recall problem, found only because a ground truth of the four weeks had been kept.

6.4.2 Seven tuning methods, the scoped exception and the record

In order of preference: (1) threshold adjustment, always with a second, slower condition rather than a higher single threshold (10 in 10 minutes or 30 in 60 minutes); (2) a scoped exception for one known, approved source of alerts; (3) context enrichment (the rule consults the calendar, the allow-list or the asset criticality); (4) correlation (two independent signals required: failures and a success; a scan and an outbound connection from the same host); (5) aggregation (one alert per source per window, with the count inside); (6) a rule logic change (replace the measured quantity: age of last success → two consecutive failed attempts); (7) closure with a reason code for benign true positives — no change to the rule. Every method is tested the same way: a replay of the last four weeks of alerts and known events through the proposed rule set, which must show false alarms down, misses not up, and the detection delay measured. Without the replay the change is an opinion.

Exceptions carry the highest risk of creating blind spots. A scoped exception names all of: the asset, the account or source address, the time window, the activity (the logon type, the target), the owner, the reason and an expiry date. "Ignore nas-sync" would also ignore an attacker who steals the nas-sync credentials; "nas-sync on SRV-AD01, 01:00 to 01:10, logon type 4, until November 15" ignores exactly one failing job. An exception without expiry is a permanent blind spot. The tuning change record has one line per change: rule, what changed, before, after, scope, reason, owner, expiry, review date; a disabled rule is recorded in the same place — tuning by deletion leaves no trace and is forbidden by the loop. The monthly review reads the record, removes expired exceptions and lists the ten noisiest rules with their false-alarm reasons.

6.4.3 Detection delay against false alarms: the A-09 rule, and the replay

Rule R4 version 1 compared the age of the last successful update with 24 hours, once a day at 09:30: it alerted 36 hours 15 minutes after the first failure of A-09 and fired five times on laptops that were simply off. Version 2 counts consecutive failed attempts (antivirus event 2001) on the same host and alerts at the second one: 4 hours after the first failure, 8 hours after the last success in the worst case, never on a silent host (a host that sends nothing is a coverage question, not a failure). MTTD (mean time to detect) fell from 36.25 hours to 4, false alarms from 5 to 0, recall stayed at 1. The replay of rule set v2 kept 9 alerts, turned 1 into INFO and suppressed 41: v1 51 alerts (7 true, 2 benign, 42 false, 1 missed) against v2 9 alerts (7 true, 1 benign, 1 false, 0 missed); overall precision rose from 0.18 to 0.89, recall from 0.86 to 1.00. Two details worth an exam line: the precision of the baseline rule R2 fell from 0.75 to 0.67 because its benign true positive became INFO and left the denominator while its one false alarm stayed — precision is always read together with the alert count; and the one remaining false alarm (a software update nobody had put in the calendar) is a process problem fixed by a recommendation, not by a rule. The six documented changes of v2: a slow-attack condition on R1; a scoped exception for nas-sync (expiry November 15, root cause fixed by a ticket); calendar context on R2; an allow-list entry for the weekly scan on R3; the logic change on R4; an allow-list entry for the vendor's contracted support window on R5.

Topic 6

Lesson 6.5 — Recommending tools and improvements

6.5.1 A recommendation is a decision document

A recommendation is a written proposal that someone with authority can accept or refuse. It has six parts, and a recommendation missing one of them is an opinion: (1) the problem and its evidence (a case identifier, a measured number, a date: "detection delay 36 h 15 min on A-09"); (2) the option proposed, with an alternative when one exists; (3) the benefit stated as a KPI before and a target after ("coverage 59 % to above 85 %"); (4) the cost in money, time, skills, storage and side effects; (5) the priority and the owner with a deadline; (6) the measure that will show, after implementation, whether the benefit arrived. Improvements fall in four categories — process changes (a verification step in the change procedure, a monthly tuning review), configuration changes (an audit policy, a syslog target, a rule), tools (an agent, a flow collector, a tap) and people (training, an on-call rota) — and the cheapest are rarely tools.

6.5.2 Selecting a tool: the criteria of Lesson 3.2 and the legal checks

Eight criteria: the need it closes (a line of the ranked gaps); the fit with our platforms and collector; the total cost of ownership (licence, hardware, storage, time to deploy and operate, training); the performance footprint measured in the lab (Lesson 6.2); the skills and support available; the licence and legal conditions (where the data is stored, personal information under Law 25, export restrictions); the security of the tool itself (authentic download verified by hash and signature, a VirusTotal check as Legal Notice Annex C asks, whether it opens new ports); and reversibility (can it be removed cleanly after a failed trial). The shortlist for a 14-person firm is mostly free software maintained by large communities: Sysmon (process and connection events on Windows, 0 CAD, about 1.5 GB per day, under 2 % CPU with a tuned configuration), the flow exporter built into OPNsense with an nfdump collector, Suricata (signatures on the mirror) and Wazuh (host agent and correlation engine once the team is trained). Every trial runs in the Authorized Lab Environment first: a defensive tool deployed on a live system without a test window and a rollback is a change that can take the network down (Legal Notice sections 6.4 and 7.4).

6.5.3 Prioritising: benefit, effort, bands

Each candidate receives two scores from 1 to 5: benefit (5 = closes a weakness behind a P1 or P2 case) and effort (1 = minutes of configuration, 5 = days of work plus training). Priority score = benefit × (6 − effort), from 1 to 25. Three bands: quick win (benefit at least 4 and effort at most 2) → done next week; planned (score at least 9) → next change window; later (the rest) → reconsidered at the quarterly review. The arithmetic is simple on purpose: the owner must be able to recompute it. Of the twelve Atelier Nordik candidates, six were quick wins, five planned and one later (the Wazuh deployment: benefit 4 but effort 5, score 4). The top three: R-01, add a verification step and a calendar entry to every change (process; benefit 5, effort 1, score 25 — it costs nothing and removes the cause of A-09); R-02, alert on two consecutive failed definition updates (configuration; 4 × 5 = 20); R-06, the source-health rule (configuration; 20). Totals: 630 CAD one-time (a network tap at 450 CAD and a 2 TB disk at 180 CAD), 0 CAD per year.

6.5.4 Two readers, and measuring afterwards

A result is written twice (Lesson 5.5). The owner memo is one page in plain words (no host names, no ticket numbers, sentences under 25 words), quick wins first, the cost in dollars, one decision requested with a reply date, and the KPIs that will measure the result; it carries TLP:AMBER+STRICT at the top and the bottom because it describes weaknesses of this organization's network. The technical annex carries TLP:AMBER with the ranked table: identifiers, evidence, side effects and owners. After approval the loop starts again: the KPIs are measured at the monthly review — reference age, monitoring volume (410 GB/day → 48 with the filter, target ≤ 50), sensor drop rate (target < 0.1 %), coverage score (58.8 % → target ≥ 85 %), needs answerable (1 of 8 → 8 of 8), alerts per week (12.8 → target < 4), precision (18 % → 89 %, target ≥ 80 %), recall (86 % → 100 %, target 100 % for P1/P2 events), MTTD (36 h 15 min → target ≤ 8 h for monitoring-health events), recommendations implemented on time (quick wins within 2 weeks).

Case Study 1 — Choosing the first monitoring tool for a dental clinic

Covers: Topic 3 › Lesson 3.1 (categories, evidence, axes) › Lesson 3.2 (need, knock-outs, weighted scoring, decision record)

Situation. Clinique dentaire du Plateau has nine employees, one Windows file server holding patient files, four workstations, one managed switch, one firewall, and a cloud appointment service with an audit log. There is no licence budget, the receptionist's brother-in-law gives 45 minutes of IT (information technology) time per day, and the only spare machine is a virtual machine with 8 GB of RAM (Random-Access Memory). The dentist writes: "I want to know when someone fails to log on to the server five times, and I want the records kept for 90 days." Four candidates are on the table: Wireshark, an open-source log platform with alerting (documented minimum 4 GB of RAM), an open-source availability monitor, and a commercial cloud SIEM (Security Information and Event Management) at 190 CAD per month.

Questions.

  1. Rewrite the dentist's wish as a testable need with its six elements.
  2. Which kind of evidence does the need require, and which category of tool must the long list come from?
  3. Write the knock-out criteria and apply them to the four candidates.

  1. "Collect the Security event log of the file server (asset), as events (evidence), raise an alert when the same account fails to log on five times within ten minutes (behaviour), within five minutes of the fifth failure (delay), by e-mail to the IT helper (recipient), and keep the events 90 days (retention)."   3. Knock-outs: K1 belongs to C1/C7; K2 zero licence cost; K3 documented minimum RAM fits 8 GB; K4 can send an e-mail alert. Wireshark fails K1 and K4 (packet analyzer, no central store, no alerting); the availability monitor fails K1 (category C3); the cloud SIEM fails K2 (monthly cost); only the log platform survives — a short list of one is still the result of the method, and the reason for each knock-out is written.
  4. Weights must be fixed before any candidate is scored, so that nobody adjusts them until the preferred product wins; the criteria and weights sum to 100, each candidate is scored 0 to 5 per criterion with one sentence of justification, and the total is Σ(weight × score) ÷ 5, a percentage. The written justifications are worth more than the arithmetic.
  5. The need, the constraints, the long list, the knock-outs with reasons, the scores, the choice, the alternatives rejected and why, the pilot plan (snapshot before, measurements, rollback), the date and a review date. The record is the starting point of the recommendations of Lesson 6.5.

Case Study 2 — A patch Sunday at a microbrewery

Covers: Topic 3 › Lesson 3.3 (seven stages, integrity, ports, update order, rollback)

Situation. Brasserie Rivière-Noire runs a Wazuh pilot on a monitoring VM; two Windows hosts have agents (version 4.14.7), the firewall and the switch send syslog. The volunteer technician downloads the 4.14.8 installer from a link posted in a brewing forum because "the official site was slow". He installs anyway, then updates the agents before the manager "because the workstations are faster to reach", skips the snapshot, and at the end notices that the manager no longer shows events from one agent. Questions.

  1. List every stage of the seven-stage procedure that was skipped or done wrong.
  2. What does the checksum mismatch mean, and what is the only correct action?

Case Study 3 — The baseline of a bookstore's file server

Covers: Topic 3 › Lesson 3.4 (observation period, buckets, statistics, polluted baseline, owner review, thresholds)

Situation. Librairie Saint-Roch measured successful logons per hour on its file server for exactly one week, Monday to Sunday. During the night of Thursday to Friday, an inventory company connected 48 times between 23:00 and 01:00 to count stock. The technician computed one mean and one standard deviation for the whole week (all hours pooled) and set the alert threshold at mean + 3σ = 31 logons per hour. The owner asks whether the next night-time stock count "will be seen".

Questions.

  1. Two errors were made before any statistics were computed. Name them.
  2. Why should buckets be used, and which bucket design did the course use for a weekday shop?
  3. Explain how the 48 inventory logons pollute the baseline and why the error is "invisible".
  4. Describe the leave-one-out test and the role of the owner review for the Thursday night hours.
  5. If the cleaned weekday 23:00 bucket has mean 0.2 and σ 0.4, what are the candidate warning and alert thresholds?

Most probable answers

  1. The observation period is too short (a single week has only one Monday and one weekend, so nothing can be compared with anything: at least two full weeks are required), and the technician changed nothing during collection but did not check that the period was normal — the inventory night should have been identified before approval.
  2. Normal activity at 09:00 on a Tuesday is not normal activity at 23:00; a single threshold for all hours is too high for the night and too low for the day. The course used one bucket per weekday hour (24 buckets) plus one pooled bucket for all weekend hours.
  3. The 48 night logons raise the mean and the standard deviation of the hours they belong to, so the threshold of those hours becomes high enough to hide the next inventory night (and a real intrusion of the same size). The baseline "works", the numbers exist, and the alarm never rings — nobody sees a tool that is quietly blind.
  4. Each hour is compared with the other values of its bucket, leaving the hour under test out, so that a large value cannot mask itself by raising its own bucket's mean and σ; any hour above the mean + 3σ of its peers is listed as suspicious. The list is brought to the owner, who decides each hour with a reason: a documented, one-time stock count is excluded; a busy but normal hour is kept. The exclusion and its reason are written in the Baseline Record, which the owner signs.
  5. The pilot applies a floor of 1 to σ (0.4 → 1.0): warning = ⌈0.2 + 2 × 1⌉ = 3, alert = ⌈0.2 + 3 × 1⌉ = 4. The next stock count at 23:00 will be noticed — and should itself be written in the maintenance calendar beforehand.

Case Study 4 — Writing and sizing an alert rule for a law office

Covers: Topic 3 › Lesson 3.5.1 (seven parts, rule types, rule card, MITRE ATT&CK reference) › Lesson 3.5.2 (profiles, k, floor)

Situation. Cabinet Lemieux & Tanguay wants two alerts: (a) "a remote desktop logon on the accounting computer outside 07:30 to 18:30 on weekdays" and (b) "an unusual amount of data sent to the Internet by that computer". For (b), fourteen days of firewall records give, for office hours, mean 22.4 MB per hour and standard deviation 6.1 (110 hours, P99 = 41.0), and for off hours mean 1.8 and standard deviation 0.7 (226 hours). The partners want "no more than one false alarm per week" and consider 15 MB per hour too small to matter at night.

Questions.

  1. Write the rule card of alert (a) with its seven parts, its rule type and its MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) reference.
  2. What is the rule type of alert (b), and why can a Wazuh rule not compute it directly?
  3. Compute the candidate office-hours thresholds for k = 2 and k = 3, and explain how to choose k from the baseline.
  4. Compute the night threshold with k = 3, and explain why the floor applies.
  5. The 99th percentile of office hours is 41.0. Should it replace the statistical threshold?

Most probable answers

  1. Data source: the accounting computer's Windows Security log through the agent. Match condition: event 4624 (successful logon) with logon type 10 (remote desktop); also type 2 if interactive logons at the keyboard are wanted. Count and window: 1 event (single-event rule with a time condition). Grouping key: the account name. Severity: Medium (frequent legitimate causes, such as the external accountant), Wazuh level 8. Notification: daily digest and dashboard, one office day to acknowledge. Response note: confirm with the account owner; if not the owner, follow the incident procedure. Reference: T1078 Valid Accounts. In Wazuh: a custom rule in local_rules.xml with the time and weekday options.

Wazuh rules compare fields and do not calculate means, so a small script computes the hourly volume, writes one status line per hour (profile, threshold, ABOVE or NORMAL) into a log file, and a Wazuh rule matches the status: "the script calculates, Wazuh alerts."

  5. Not blindly. The percentile is compared with the statistical threshold and with the real counts: a P99 of 41.0 means one office hour in a hundred exceeds 41 during a normal fortnight, so using it as the threshold would already produce about one false alarm per 100 office hours; the comparison on the data decides, and the chosen value, the k and the floor are written in the threshold sheet with the baseline period and the date of calculation (recalculated when the baseline is updated, reviewed at least monthly — CIS safeguard 13.11).

Case Study 5 — Alert fatigue at an accounting firm

Covers: Topic 3 › Lesson 3.5.3 (severity, channels, e-mail defaults, acknowledgement, escalation, four controls) › Lesson 3.5.4 (outcomes, precision, recall, regression testing)

Situation. Comptabilité Bélanger has a monitoring technician with 60 minutes per day. Last Tuesday, Wazuh produced 31 notifications: 19 copies of "log source silent" for the same firewall during a 45-minute outage, 7 Medium "logon outside office hours" alerts, 3 High and 2 Critical. The two Critical alerts (level 14) were e-mailed; the three High alerts (level 10) never reached the mailbox. One Critical alert was acknowledged after 40 minutes.   1. Why did the High alerts not arrive by e-mail, and what are the two fixes?
  2. Which two of the four controls would have reduced the 31 notifications the most, and how?
  3. Was the Critical acknowledgement acceptable? What should have happened at minute 15?
  4. Compute precision and recall of the rule set. Which of the two faulty outcomes is more dangerous, and why?
  5. After correcting the two rules, what must be done before trusting the new version?

  1. By default Wazuh e-mails only alerts of level 12 or more (email_alert_level); High alerts at level 10 fall below. No. The acknowledgement target for a Critical alert is 15 minutes; when nobody acknowledges within that time, the escalation path notifies the next role — at Val-des-Pins the owner is called by phone 15 minutes after the alert. Case Study 6 — The missing weekend at a veterinary clinic

Covers: Topic 4 › Lesson 4.1 (six questions, time zones, audit policy, size and overwrite, central collection, the seven checks, syslog PRI)

Situation. Clinique vétérinaire des Laurentides noticed on Monday that its Windows server's Security log starts at Sunday 23:10: everything before it is gone, although nobody cleared it. The server's clock is five minutes ahead of the firewall's. The Linux reception kiosk writes its authentication messages in local time without a year. The clinic has no central log server. A consultant proposes "a firewall rule to block the attacker", though no attacker has been identified.

Questions.

  1. Give the most probable explanation for the missing Security events, and the command that shows the relevant setting.
  2. Which three of the seven checks before trusting a log failed here, and why?
  3. What does central collection change, and which retention would the course use as a minimum?
  4. The kiosk sends a syslog message from facility authpriv (10) with severity notice (5). What is its PRI value, and what do the two numbers mean?
  5. Why is the consultant's proposal outside what this course allows, and what should be written instead?

Most probable answers

  1. A Windows channel has a maximum size (about 20 MB by default) and overwrites its oldest events when full; a busy weekend filled the Security log and the old events were discarded. wevtutil gl Security shows the size and the retention setting; nothing was cleared (no event 1102), the log simply wrapped. The fix is a larger log and, above all, forwarding.
  2. Clock — a five-minute difference means events of the server and the firewall cannot be put in order (NTP synchronisation and a known time zone are needed; the kiosk's time stamp has no year and no zone, so the parser must add them). Completeness — the gap from Friday to Sunday 23:10 would be read as "nothing happened". Integrity / retention — the only copy lived on the server itself, where it could be overwritten (or cleared by a local administrator); no central copy existed. (Coverage would be a fourth: the audit policy must record the categories needed.)
  3. Every entry is copied, as soon as it is written, to a system the hosts cannot modify: the copy survives the clearing, filling or failure of the local log; all hosts become searchable together in one format; and retention is decided by the plan, not by the local file size. The course minimum is 90 days (CIS safeguard 8.10; NIST SP 800-92).
  4. PRI = facility × 8 + severity = 10 × 8 + 5 = 85. The facility says which subsystem produced the message (authpriv: security and authorization messages, private); the severity says how serious it is, from 0 emergency to 7 debug, where a lower number is more serious.
  5. Alerts inform; people decide the actions. Any blocking or containment on a real system requires the owner's written approval, a change window and a tested rollback (Legal Notice section 7.4), and here there is not even a diagnosis. What should be written is the evidence (the seven checks applied, the gap documented), then the analysis of Lesson 5.3 — and a change request for central collection.

Case Study 7 — Planning and reading a capture for a landscaping company

Covers: Topic 4 › Lesson 4.2 (capture points, storage arithmetic, tcpdump options, capture filter versus display filter, capture record, legal frame, the five reading questions)

Situation. Paysages Beaulieu's firewall records show that the estimator's workstation (10.30.1.25) sent 390 MB to the Internet at 03:00 on two consecutive nights. The firm has a managed switch, an unmanaged switch in the garage, a monitoring server with a second network interface, and a guest Wi-Fi used by clients in the showroom. The owner has authorized, in writing, a capture of that workstation's traffic for one night. The technician proposes to capture "everything on the showroom Wi-Fi as well, to be sure".

Questions.

  1. Which capture point should be used, and why not the workstation itself or the garage switch?
  2. Write the tcpdump command for the plan: one file per hour, stop after eight files, headers only, no name resolution, syslog to the monitoring server excluded.
  3. What must the capture record contain so that the capture is evidence?
  4. Why must the showroom Wi-Fi proposal be refused?
  5. The capture shows a DNS (Domain Name System) answer for a name with a 300-second TTL (Time To Live), a complete three-way handshake to port 443, a ClientHello with a server name, then 1,514-byte frames at 89 per second. Answer the five reading questions, and say what the capture cannot tell.

Most probable answers

  1. A mirror (SPAN) port on the managed switch copying the workstation's port to the monitoring server's second interface. On the workstation itself the user could see, stop or alter the capture, and a possibly compromised host is not a trustworthy observer; the unmanaged garage switch cannot mirror anything. (A TAP on the workstation's cable would also work but needs an interruption to install.)
  2. tcpdump -i <mirror-interface> -n -s 256 -G 3600 -W 8 -w est-ws_%Y-%m-%d_%H%M.pcap -Z <user> 'host 10.30.1.25 and not port 514' — -s 256 keeps every header and the TLS (Transport Layer Security) server name while dropping most content; -n prevents the capture host from sending DNS queries while observing; -G 3600 -W 8 bounds the capture in time so that it cannot fill the disk; the capture filter in BPF syntax decides what is written and cannot be undone.
  3. The authorization reference (the owner's written authorization), the operator and the start time (UTC and local), the capture point and the interface, the filter and the snapshot length, the tool and its version, the file names with their sizes and SHA-256 hashes, the stop time and reason, the storage location and the deletion date. The hash proves that the file analysed is the file captured.
  4. Capturing on a network shared with other people is interception (Criminal Code section 184), whatever the intention; the clients on the guest Wi-Fi have not authorized anything, and the authorization covers one workstation for one night. Legal Notice section 7.2: never promiscuous mode on a shared network; every capture is personal information; the guest network is excluded from every capture and every log.
  5. Who with whom: the workstation and the address resolved from the DNS name, one conversation dominating the bytes. How much: the workstation sends far more than it receives, which is unusual for a workstation. When: from 03:00, at a steady rate (89 frames of 1,514 bytes ≈ 135 kB/s ≈ 486 MB per hour). Which service: port 443 with the server name announced in the ClientHello. How it started: a complete handshake, so the connection was opened normally by a program on the workstation. What the capture cannot say: which program and which account sent the traffic, and the content of the encrypted session; those come from the host logs (process creation with the command line, or the Sysmon network connection event). The TTL of 300 seconds is an observation to record, not a proof of anything.

Case Study 8 — The Saturday queue of a physiotherapy clinic

Covers: Topic 5 › Lesson 5.1 (z-score, families, outcomes) › Lesson 5.2 (five questions, impact and confidence, bands, hand rules, calendar pitfall)

Situation. Physio Mont-Royal (asset criticality: domain controller 5, monitoring server 4, workstations 2) has five alerts on Saturday at 14:00. A-1: the baseline rule flagged the reception workstation at 20:00 on Friday with 38 outbound connections (baseline for that hour: mean 2, σ 1.4). A-2: 14 failed logons on the "administrator" account of the domain controller at 02:35 from a VPN address not in the allow-list (rule severity 4). A-3: the backup account's batch logon on the domain controller at 02:00 (calendar: backup window 02:00–03:00, asset = domain controller, account = backup account). A-4: the monitoring server's log disk at 88 % (rule severity 2). A-5: a clock drift of 3 seconds on one workstation (informational rule, severity 1).

Questions.

  1. Compute the z-score of A-1 and name the anomaly family. Would the two-condition detector of the course flag it?
  2. Score A-2: impact, confidence, priority and band.
  3. Score A-4 and apply the hand rule.
  4. Why is A-3 closed as benign, and why would a calendar entry matched on asset and time only be dangerous for A-2?
  5. Order the queue and give the decision for each band.

Most probable answers

  1. z = (38 − 2) ÷ 1.4 = 25.7; an ordinary value at an abnormal time on a workstation that is idle at 20:00: a contextual anomaly. Yes: |z| ≥ 3 and the absolute difference (36) is ≥ 10, so both conditions hold; with a second flagged hour it would also be collective.
  2. Impact = max(severity 4, criticality 5) + 1 for the privileged account = 6, capped at 5. Confidence: start 3, +1 for an address neither local nor allow-listed = 4 (no other open alert on the same asset, so no corroboration). Priority = 5 × 4 = 20, P1: acknowledge within 15 minutes, open the incident record, call the owner and the contractor.
  3. Impact = max(2, 4) = 4; confidence 3 (nothing explains it, no corroboration); priority 12, P2 — and an alert about the health of the monitoring is never ranked below P2 in any case, because while the disk fills every other detection becomes a potential false negative.
  4. A-3 matches the calendar on asset, time and activity (the backup account's batch logon inside its window), so confidence is forced to 1 and it is closed with the reference to the calendar entry. If the window were matched on asset and time only, the fourteen failures on "administrator" at 02:35 would also have been excused as "expected activity": attackers do not consult the calendar, but they like quiet hours; every exception must name the activity it excuses.
  5. P1: A-2 (20). P2: A-1 (impact max(rule severity, 2) with confidence 3 and the +1 if the destinations are external; at least 6 to 10 — investigate today) and A-4 (12, health). P3/P4: A-5 (informational, confidence 3 − 1 = 2, impact 2 → 4, P4: monitor, close if quiet for 7 days — but clock drift matters for correlation and feeds Topic 6). Benign: A-3, closed with its reason. The queue is read as a story: someone is guessing the administrator password through the VPN, a workstation woke up on Friday evening, and the monitoring server is running out of disk.

Case Study 9 — From analysis to the owner's note at a print shop

Covers: Topic 5 › Lesson 5.3 (five steps, independence, hypothesis results) › Lesson 5.4 (category, root cause, exposure window, confidence, evidence integrity) › Lesson 5.5 (need-to-know, TLP, plain language, notification duties)

Situation. Imprimerie Deschamps' monitoring showed that the agent of its order-entry server stopped sending logs on Wednesday at 22:40; the alert came on Friday at 09:30 from the daily health check. On Monday the technician exported the server's local System and Application logs, the monitoring console's agent status history, the contractor's change log and the maintenance calendar; the change log shows a disk-cleanup script deployed on Wednesday at 22:30 with no verification step, and the server's local log shows the agent service stopped at 22:40 by that script. A phone call to the contractor at the number in the contract confirmed the script and the omission. The agent was restarted on Monday at 10:15; no sign of unauthorized access was found in the local logs, which were never interrupted. No personal information was involved.

Questions.

  1. Build the hypothesis table (benign first) and give the result of each test.
  2. How many independent groups support the conclusion, and what confidence level follows?
  3. Decide the category with the three questions, in order, and state the root cause as a process fact.
  4. Measure the exposure window and the detection delay.
  5. Which recipients, which TLP (Traffic Light Protocol) labels, and which legal notification checks apply? Write the first two sentences of the owner's note in plain language.

Most probable answers

  1. H1 (benign): the server was off or disconnected — refuted (the local logs continued without interruption; the console showed the host online). H2 (benign): a documented change explains it — supported (change log: cleanup script at 22:30; local System log: agent service stopped at 22:40 by the script; console: agent status "disconnected" from 22:40; calendar: the change absent). H3 (adversary, ATT&CK v19 T1685 Disable or Modify Tools, tactic TA0112 Defense Impairment): someone stopped the agent to hide activity — not supported (usual contractor account, approved ticket, no unauthorized access in the uninterrupted local logs) and confirmed out of band by phone. Each hypothesis was written with its prediction before the evidence was read in detail.
  2. Four groups: the server's local logs, the console, the change log, the calendar; the phone call at the contract number is a fifth, out-of-band source. Three or more agreeing groups with no contradicting record and an explained mechanism: high confidence ("the evidence shows that…").
  3. Question 1, unauthorized actor or policy violated: no (approved ticket, usual account, confirmed by phone). Question 2, monitoring or protection tool failing: yes. Category: monitoring failure. Immediate cause: the cleanup script stopped the agent service. Root cause: the change process allowed a script to be deployed without a verification step and without a maintenance-calendar entry, so nothing checked that the agent was still running — a fact about a process, not a judgment about the contractor.
  4. Exposure window: from the moment the agent stopped (Wednesday 22:40) to the verified restart (Monday 10:15): 4 days 11 hours 35 minutes, measured from evidence, not from the alert. Detection delay: Wednesday 22:40 to Friday 09:30 = 34 hours 50 minutes. (With a 30-minute source-health rule the alert would have come at about 23:10.)
  5. Recipients: the owner (decision maker; phone first, then the note; TLP:AMBER+STRICT), the contractor (technical annex in ITSAP.40.003 order; TLP:AMBER), the users of the order-entry system if they must know whom to call (short message; TLP:GREEN); deliberate non-recipients with reasons: clients, the Commission d'accès à l'information, the Office of the Privacy Commissioner, the Cyber Centre, the police. Checks: Law 25 — no personal information accessed, used, communicated or lost, so not a confidentiality incident, no notice, no register entry, reasoning kept in the file; PIPEDA — no breach of security safeguards; Cyber Centre — no attack; police — no crime. Owner note: "From Wednesday evening to Monday morning, the order-entry server stopped sending its activity records to our monitoring. This came from a mistake in a planned cleanup, not from an attack." (No host name, no ticket number, no code; sentences under 25 words.)

Case Study 10 — Optimising the monitoring of a grocery cooperative

Covers: Topic 6 › Lesson 6.1 (baseline update, exclusions) › Lesson 6.2 (strategies, the rule above cost) › Lesson 6.3 (coverage score, gap weight, source health) › Lesson 6.4 (precision, scoped exception, replay) › Lesson 6.5 (priority score, bands, owner memo)

Situation. Coop alimentaire du Vieux-Port has four assets: the point-of-sale server (criticality 5), the firewall (5), the office server (4) and a workstation pool (2). Its coverage matrix requires three sources per asset (12 cells); 6 cells are collected, 2 are "available but not collected" (both on the firewall) and 4 are missing (two on the point-of-sale server, two on the pool). In four weeks the rules produced 40 alerts: 6 true, 1 benign, 33 false (30 of them from one till account whose scheduled job uses an expired password every night at 01:05) and 1 real event missed. The mirror port receives 24 Mbit/s on average. Three improvements are proposed: P-1 rotate the till account's password and add a verification step to changes (benefit 5, effort 1, 0 CAD); P-2 a network TAP on the firewall link (benefit 3, effort 3, 450 CAD); P-3 a source-health rule (benefit 4, effort 1, 0 CAD).

Questions.

  1. Compute the coverage score.
  2. Compute the precision and recall of the current rule set, and name the cause of most false alarms with its remedy.
  3. If an exception is written for the till account while the password is being fixed, what must it name?
  4. Compute the daily volume of the mirror and say which strategy keeps the detections at the lowest cost, and which strategy is rejected for detection.
  5. Score and band the three proposals, and write the "decision requested" line of the owner memo with its label.

Most probable answers

  1. Required weight = 3 cells × (5 + 5 + 4 + 2) = 48. Collected weight: assume the 6 collected cells are the three of the office server (12) and one on each of the other three assets (5 + 5 + 2 = 12), total 24; the two partial firewall cells count one half each: 2 × 0.5 × 5 = 5. Score = (24 + 5) ÷ 48 = 60.4 %. (In the exam, show the formula Σ(criticality × collected) ÷ Σ(criticality × required) and the half weight of a partial source; the exact split of the collected cells must be stated as an assumption if the case does not give it.) The two missing cells on the point-of-sale server have gap weight 5 × (needs blocked, at least 1) each and rank first unless a cheaper closure ties.
  2. Precision = (6 + 1) ÷ 40 = 17.5 % (benign true positives count as correct alerts, as in the KPI table); recall = 6 ÷ 7 = 85.7 %. The cause is a stale reference (an expired service-account password); the remedy is to fix the password — a process change — not to raise the threshold.
  3. The asset (the point-of-sale server), the account (the till account), the time window (01:00 to 01:10), the activity (the scheduled job's logon type, the target), the owner, the reason (ticket number of the password fix) and an expiry date; "ignore the till account" would be a permanent blind spot that also excuses an attacker who steals that account.
  4. 24 × 1,000,000 ÷ 8 × 86,400 ≈ 259 GB per day for a full capture. A filtered capture (bulk backups and vendor downloads removed) or flow records keep the detections at a fraction of the bytes; flow records lose only the payload and only see what crosses the exporter. Sampling is rejected for detection: at 1:10 a short scan cannot reach a 10-port rule and a handful of connection attempts survive only about half of the time. The rule above cost: never remove the data a detection rule depends on — coverage is decided before cost.
  5. Priority = benefit × (6 − effort): P-1 = 5 × 5 = 25, quick win (benefit ≥ 4 and effort ≤ 2); P-3 = 4 × 5 = 20, quick win; P-2 = 3 × 3 = 9, planned (score ≥ 9 but effort 3 excludes a quick win). Memo line, under the label TLP:AMBER+STRICT at the top and the bottom: "Decision requested: approve the two quick wins for next week at no cost, and the firewall copy device (450 dollars) for the next change window. Reply by Friday." Then the KPIs: alerts per week now 10, target under 4; share of correct alerts now 18 %, target above 80 %; coverage now 60 %, target above 85 %.

The three functions

MCQ 2

Kinds of evidence

Covers: Topic 3 › Lesson 3.1 › 3.1.2 The five kinds of evidence

A firewall exports, for each connection it handled, the two addresses, the protocol, the ports, the start time, the number of packets and the number of bytes, without any content. This export is best described as:

MCQ 7

Checksum mismatch

MCQ 14

Polluted baseline

Covers: Topic 3 › Lesson 3.4 › 3.4.4 Cleaning, validating and documenting

Why does the leave-one-out test compare each hour with the other values of its bucket, excluding itself?

Answer: (B)

MCQ 15

Rule types

A rule fires when a successful logon of an account occurs less than ten minutes after a burst of failed logons of the same account. Its type, and what the tool must remember, are:

Answer: (B)
Explanation. Different events in a given order within a time window define a sequence (correlation) rule; the tool must remember that the first event (the burst) happened. A threshold rule counts identical events, an absence rule watches for missing events, a single-event rule remembers nothing.

Essay 4

Integrity verification, snapshot and rollback

Covers: Topic 3 › Lesson 3.3 › 3.3.2 and 3.3.5

Explain what a checksum and a digital signature prove, why a snapshot is taken before an installation or an update, and what "rollback" means in the course.

Hint. SHA-256, 64 hexadecimal characters; GPG; "MON-01 pre-install 4.14.7"; immediately, before the next host.
Model answer. A checksum is a fixed-length number computed from the entire content of a file with a hash function; with SHA-256 (Secure Hash Algorithm, 256-bit) it has 64 hexadecimal characters and changes completely when a single byte changes, so a value equal to the one published by the vendor proves that the downloaded file is byte-for-byte the published file, and a mismatch means the file is corrupted or tampered and must be deleted and downloaded again from the official source. A digital signature is a checksum signed with the publisher's private key and verified with the public key (typically GPG, GNU Privacy Guard): it proves integrity and origin at once, and package repositories verify it automatically once the signing key is installed. A snapshot of the virtual machine, named with the date and the reason, is taken before every installation and update because it is the tested way back: section 6.4 of the Legal Notice asks for it, and in a small organization the snapshot is also the test environment. A rollback returns a component to its state before the change — restoring the snapshot for the whole server, re-installing the previous package for one agent — immediately when verification fails, before the next host is touched, with a ticket that records the failure for later root-cause work. No change is made without a tested way back.
Why this answer is right. It distinguishes checksum from signature as in 3.3.2, states the only correct action on a mismatch, and defines rollback with its timing rule from 3.3.5.

Building a baseline that can be trusted

Covers: Topic 3 › Lesson 3.4 › 3.4.3 and 3.4.4

Explain how the course builds a baseline of successful logons per hour for a file server, from the observation period to the signed record, and how a polluted baseline is caught.

Hint. Two full weeks; 24 weekday buckets + 1 weekend bucket; mean, σ, p95; floor of 1; leave-one-out; owner review; version and sign-off.
Model answer. The metric and the source come from the monitoring plan, in priority order. The observation period lasts at least two full weeks, because organizations live on a weekly cycle and a single week has only one Monday; nothing is changed on the system during collection. Hours are grouped into time buckets expected to behave the same way — one bucket per weekday hour of the day plus one pooled bucket for all weekend hours — and three statistics are computed per bucket: the mean, the standard deviation σ (with a floor of 1, because an always-zero hour would otherwise give a threshold of zero) and the 95th percentile. The list goes to the owner review, where each hour receives a decision with a reason — a documented migration test is excluded, a busy delivery afternoon is kept — and the statistics are recomputed on the kept hours. The Baseline Record (identifier with version, period, kept and excluded observations with reasons, bucket definition, statistics, candidate thresholds, reviewer, approver, date, next review) is signed by the system owner, who is accountable for the exclusions.

Testing before trusting: outcomes, ratios and regression

Covers: Topic 3 › Lesson 3.5 › 3.5.4 Testing, tuning and documenting alerts

Hint. TP, FP, FN, TN; precision = TP ÷ (TP + FP); recall = TP ÷ (TP + FN); regression testing; the register.
Model answer. A rule that has never fired may be correct or broken, and only a test shows which. Essay 11

How a detector decides, and the two practical rules

Covers: Topic 5 › Lesson 5.1 › 5.1.5 How a detector decides "unusual"

Present the five detection methods and explain the two practical rules that the course adds to the statistical method, with a numeric example.

Hint. z = (observed − mean) ÷ σ; long clean baseline; minimum absolute difference; 2 ± 1.2 and 6.
Model answer. A detector turns records into a decision. Signature-based detection compares each record with known bad patterns: precise for known threats, blind to new ones, and strictly not anomaly detection. Threshold-based detection counts records in a window against a fixed number chosen by a person from the baseline and the policy (10 failures in 10 minutes): simple, transparent, easy to tune. Statistical detection computes the mean and the standard deviation σ of the baseline and measures the z-score, z = (observed − mean) ÷ σ, with a common tolerance of |z| ≥ 3, beyond which fewer than 0.3 % of normal observations fall for a bell-shaped metric. Behavioural (profile-based) detection keeps the baseline per entity and per context — is this value normal for this host at this hour? — which commercial products call UEBA (User and Entity Behavior Analytics). Machine learning learns the shape of normal from many variables at once and is not used in the course. Two rules complete the statistical method. First, a statistical test needs a long, clean baseline: three days of data, or a period that contained an incident, give a band that is either too narrow (constant false alarms) or too wide (misses). Second, a minimum absolute difference must be added, because a tiny baseline makes small changes look extreme: with mean 2 and σ 1.2, an observation of 6 gives z = 3.3 and would be flagged, although four extra connections at night mean nothing; the course's detector flags an hour only when |z| ≥ 3 and the difference is at least 10. Good detectors combine conditions; a single number rarely suffices.
Why this answer is right. It names the five methods with the lesson's characterization of each and reproduces the two rules with the exact worked example.

Model answer. Step 1, collect: copy with read-only methods the records that concern the alert's assets, accounts and addresses over a window that starts before the first symptom, write a collection log (who, when, how, from which system, which independence group, which phase) and hash every file at collection; the output is the collection log with hashes, and the common mistake is changing the system before collecting. Step 2, timeline: convert every time to one zone, sort, quote each record verbatim with one separate interpretation, group identical repeats with their count; the output is the timeline file, and the mistake is mixing UTC and local time. Step 3, benign first: write each hypothesis with its prediction, test the benign ones first (calendar, ticket, allow-list, logbook) and then always the adversary hypothesis; the output is the hypothesis table with a result for each (supported, refuted, not supported, undetermined), and the mistake is testing only the explanation you already prefer. Step 4, corroborate: count the independent groups behind the supported explanation, two records of one system counting once; the output is the number of independent groups, at least two for a finding and three for high confidence. Step 5, conclude: write the category, the ATT&CK technique if there is an attacker, the confidence and the open questions, using exact words — "no evidence of an attack" is not "there was no attack". The three errors prevented are confirmation bias (writing hypotheses before reading the evidence in detail), mixed time zones (a console in UTC and a queue in local time can place a cause after its effect) and the single source (one system can display a wrong status; a console account can be used by someone else — hence out-of-band confirmation by phone at the number in the contract). The method is reproducible: another technician with the same files reaches the same conclusion.

Category, root cause and exposure window of case A-09

Using case A-09, show how the three questions decide the category, how the root cause is found by asking "why?", and how the exposure window and the detection delay are measured.

Hint. Monitoring failure; the change process; Thursday 21:15 to Tuesday 10:46 (4 d 13 h 31 min); Saturday 09:30 (36 h 15 min).
Model answer. Question 1 — did someone act without authority or violate a policy? No: the change was made by the contractor's usual account from its usual address under an approved ticket, confirmed by phone at the contract number. Question 2 — is a monitoring or protection tool failing? Yes: three workstations had antivirus definitions 4.5 days old. The first "yes" decides: a monitoring failure. Essay 15

Evidence integrity and chain of custody

Covers: Topic 5 › Lesson 5.4 › 5.4.8 Evidence integrity and chain of custody

Explain how hashes, the evidence register and the chain of custody protect the integrity of evidence, and which practical rules the course gives for handling evidence files.

Hint. SHA-256 properties; register fields; recompute and compare; originals read-only; spreadsheet warning; Legal Notice 7.8.
Model answer. A hash value is a fixed-length number computed from the bytes of a file; with SHA-256 (NIST FIPS 180-4) it has 256 bits written as 64 hexadecimal characters, the same bytes always give the same value, a single changed byte changes the value almost completely (changing one letter in a copy of the maintenance calendar changed 60 of the 64 characters), and it is computationally infeasible to build a different file with the same value. The evidence register lists every evidence file with its identifier, source system, independence group, collector, time, method, size and hash; integrity verification recomputes the hash later and compares it with the register, and equal values show that the file is byte-for-byte the one collected. The chain of custody records every person who held the evidence, when and why, from collection to the end of the case (RFC 3227; NIST SP 800-86). Practical rules: hash at collection, keep the originals read-only, work on copies, record every transfer, and never open an evidence file with a program that saves automatically — a spreadsheet that reformats dates and saves the file changes its bytes and its hash. A course exercise is not admissible forensic work: at work, the employer's incident response plan and chain of command apply (Legal Notice section 7.8).
Why this answer is right. It states the three properties of the hash, the role of the register and the custody record, and the handling rules exactly as 5.4.8 presents them.

Communicating one set of facts to four audiences

Covers: Topic 5 › Lesson 5.5 › 5.5.2 to 5.5.7

Explain how the course decides who is told, with which label and in which words, and why all messages must come from a single source of facts.

Hint. Need-to-know with a reason for every "no"; TLP 2.0 labels; speak before you act, write after you verify; owner note (five parts, 25 words) versus technical annex (ITSAP.40.003 order).
Model answer. Essay 17

Updating a baseline without poisoning it

Covers: Topic 6 › Lesson 6.1 › 6.1.2 Updating a baseline without poisoning it

Explain the four rules for updating a baseline, why the baseline file stores n, the mean and the standard deviation rather than raw counts, and what baseline poisoning does to a detector.

Hint. Bounded window; exclusions; separate profile with at least five samples; version and change record; pooled mean; 19:00 hour example.
Model answer. First, the update uses a bounded window of the last four to six weeks of workdays; weeks inside the window are pooled, and an old week is dropped by leaving it out of the pool, not by subtracting it. Second, the hours of a confirmed incident are excluded: an incident takes precedence over the calendar, and the excluded hours are listed with their case identifier. Third, approved-but-different activity (the Patch-Wednesday update push, which produces 112 connections against a workday mean of 63) goes into a separate profile rather than widening the band of every Wednesday, and that profile is used only once it has at least five samples; until then the calendar provides the context. Fourth, the new baseline is written as a new version next to the old one, with a change record giving, for each hour, the old statistics, the values added, the values excluded and the new statistics — a reference database is never edited in place. The file stores, per hour, the sample count n, the mean and the standard deviation, because with these three numbers an old group and a new group can be combined exactly: pooled mean = (n₁ × m₁ + k × m₂) ÷ (n₁ + k), and the variance has a corresponding pooled formula, so the raw counts are not needed. Poisoning, or contamination, is what happens when incident hours enter the statistics: if the scan hours of Thursday had been included, the 19:00 mean would have moved from 3 to about 6 and its standard deviation from 1.5 to about 12, so the next scan at 19:00 would score z ≈ 3.5 instead of 29 and the following week would fall below the threshold — the detector loses sensitivity without any rule being changed, which is the most common way a baseline fails.
Why this answer is right. It states the four rules, the storage reason with the pooling formula, and the poisoning arithmetic of 6.1.2.
Essay 18

Coverage: matrix, score and the heartbeat rule

Covers: Topic 6 › Lesson 6.3 › 6.3.1 to 6.3.3

Define monitoring coverage, explain how the coverage score and the gap ranking are computed, and describe the source-health rule and why it ranks P2.

Hint. Three dimensions; collected / available but not collected / missing / not applicable; Σ(criticality × collected) ÷ Σ(criticality × required), partial = one half; gap weight = criticality × needs blocked; 30 minutes.
Model answer. Coverage is the share of what we need to observe that we actually observe, in three dimensions: the assets weighted by criticality, the data sources, and the detection needs (the questions the rules and analysts must be able to answer). The coverage matrix puts assets in rows and sources in columns, each cell marked collected, available but not collected, missing or not applicable; a required cell that is not collected is a gap, and a gap that prevents a question from being answered is a blind spot. Coverage is not volume: a mirror port can deliver hundreds of gigabytes a day from one segment while the firewall, the VPN pool and the workstations' process logs remain gaps. The score is Σ(criticality × collected cells) ÷ Σ(criticality × required cells), a partial source counting one half; at Atelier Nordik in October it was 70 ÷ 119 = 58.8 %, and a missing source on the domain controller (criticality 5) costs five times a missing source on a workstation. Gaps are ranked by weight = criticality × number of needs blocked (at least 1), ties going to the cheapest closure, so the first cell to close is not the biggest gap but the best weight-to-effort ratio. The largest single improvement of coverage is usually a rule about the existing sources: a source-health (heartbeat) rule alerts when a source that normally produces events has produced none for a defined interval — 30 minutes for servers and the firewall — using the expected rate of each source and the maintenance calendar (a planned reboot is not silence) as inputs; it ranks P2 by the hand rule, because silence is indistinguishable from an attacker who disabled logging, and it would have found the silent web server at 11:50 on Saturday instead of during triage on Sunday.
Why this answer is right. It reproduces the definition, the matrix states, the score and ranking formulas with the course's numbers, and the heartbeat rule with its P2 justification from 6.3.
Essay 19

Tuning with a replay: the R4 rule

Covers: Topic 6 › Lesson 6.4 › 6.4.2 and 6.4.3

Explain why "tuning means raising precision without lowering recall", how a tuning change is verified, and what changed between versions 1 and 2 of the definition-update rule.

Hint. Replay of four weeks: false alarms down, misses not up, delay measured; age of last success → two consecutive failures; 36.25 h → 4 h; 5 → 0 false alarms; recall 1.
Model answer. Precision = TP ÷ (TP + FP) is the share of alerts that were correct, the ratio the analyst experiences directly; recall = TP ÷ (TP + FN) is the share of real events that were detected, what the organization discovers after an incident. Raising a threshold to silence false alarms lowers recall, so tuning must raise precision while keeping recall — which is why a threshold adjustment is always made with a second, slower condition (10 failures in 10 minutes or 30 in 60) rather than a higher single number, and why the seven methods are ordered: threshold adjustment, scoped exception, context enrichment, correlation, aggregation, rule logic change, closure with a reason code for benign true positives. Every change is verified the same way: a replay of the last four weeks of alerts and known events (the ground truth) through the proposed rule set, which must show false alarms down, misses not up, and the detection delay measured; without the replay the change is an opinion. Rule R4 version 1 compared the age of the last successful update with 24 hours, once a day at 09:30: it alerted 36 hours 15 minutes after the first failure of A-09 and fired five times on laptops that were simply switched off, because the age of the last success does not represent the failure. Version 2 is a rule logic change: it counts consecutive failed attempts (the antivirus event 2001) on the same host and alerts at the second one, four hours after the first failure and eight hours after the last success in the worst case, never on a silent host — a host that sends nothing is a coverage question, not a failure. In the replay the mean time to detect fell from 36.25 hours to 4, the false alarms from 5 to 0, and recall stayed at 1; the change is recorded with rule, before, after, scope, reason, owner and review date.
Why this answer is right. It gives both ratios with their meaning, the replay criteria, the ordered methods and the exact before/after of R4 from 6.4.
Essay 20

Writing a recommendation the owner can decide on

Covers: Topic 6 › Lesson 6.5 › 6.5.1 to 6.5.4

Describe the six parts of a recommendation, the priority score with its bands, and the differences between the owner memo and the technical annex.

Hint. Problem with evidence, option, benefit as KPI, cost, priority and owner, measure; benefit × (6 − effort); quick win / planned / later; TLP:AMBER+STRICT versus TLP:AMBER.
Model answer. A recommendation is a written proposal that someone with authority can accept or refuse, and it has six parts: the problem and its evidence (a case identifier, a measured number, a date — "detection delay 36 h 15 min on A-09"); the option proposed, with an alternative when one exists; the benefit stated as a KPI before and a target after ("coverage 59 % to above 85 %"); the cost in money, time, skills, storage and side effects; the priority and the owner with a deadline; and the measure that will show afterwards whether the benefit arrived — a recommendation missing one of them is an opinion. Improvements fall into four categories, process, configuration, tools and people, and the cheapest are rarely tools: the top-ranked item at Atelier Nordik, adding a verification step and a calendar entry to every change, cost nothing and removed the cause of A-09. Each candidate receives a benefit score (5 closes a weakness behind a P1 or P2 case) and an effort score (1 minutes of configuration, 5 days of work plus training), and priority = benefit × (6 − effort), from 1 to 25; quick wins have benefit at least 4 and effort at most 2 and are done next week, planned items have a score of at least 9 and go to the next change window, the rest is reconsidered at the quarterly review — the arithmetic is simple on purpose, so that the owner can recompute it. Tools are selected with the eight criteria (need, fit, total cost of ownership, performance footprint, skills and support, licence and legal conditions including data location under Law 25, security of the tool itself with an authentic verified download, reversibility) and tried in the lab first. The owner memo is one page in plain words — no host names, no ticket numbers, sentences under 25 words — with the quick wins first, the cost in dollars, one decision requested with a reply date and the KPIs that will measure the result, labelled TLP:AMBER+STRICT at the top and the bottom because it describes weaknesses of this organization's network; the technical annex, labelled TLP:AMBER, carries the ranked table with identifiers, evidence, side effects and owners for the contractor. After approval the loop starts again and the KPIs (alerts per week, precision, coverage score, time to detect, reference age, recommendations implemented on time) are measured at the monthly review.
